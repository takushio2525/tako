# usage 分析: ログイン・プロジェクト・機能ごとに利用制限の使い道を見る（エピック #2192 / S0）

> スライス（§9）の worker がこれを読んで実装に入れる粒度で書く。方針の正本は #2192 の本文。
> ここに書くのは「実物で確かめたこと」「決めたこと」「切り方」。
> 実測は 2026-10-16、Claude Code **2.1.301**・tako **v0.8.35**・この開発機の実データで行った。
> **会話記録は使用量のメタデータ（usage・model・timestamp・cwd・gitBranch・sessionId・message.id）だけを読み、
> 本文（message の content）は読んでいない・出力していない・保存していない**。数値は比率と桁に丸め、
> プロジェクト名・実パス・ログイン名は伏せた（プロジェクトは使用量の多い順に P1, P2, …、ログインは A / B）。

## 0. 結論（決めたこと）

| 論点 | 決定 | 根拠の節 |
|---|---|---|
| 「利用制限をどれだけ使ったか」 | **観測した used_percent の増分を、観測点の間の区間ごとに、その区間のローカルの使用量の比でキーへ按分する**（区間按分）。合計は観測と必ず一致する。観測が無い期間だけ、直近の換算係数で割った値を「推定」と明示して出す | §2 |
| 按分の重み | **API 換算**（モデル別単価 × 5 成分。fast は 2 倍）。生のトークン総量は量として併記する | §2.3 |
| 利用制限の単位 | **ログイン**（起動に使った資格情報のファイル `.claude.json` の `oauthAccount.accountUuid` の塩付きハッシュ）。tako のアカウント（設定 dir）はその下の段。この機では 4 アカウントが 2 ログインに収まっていた | §1.3 |

| 鍵の持ち方 | **取り込んだ時点で鍵を索引へ写す**（カタログ 500 件・レジストリ 200 件の追い出しと transcript の 30 日の削除より長く残すため） | §3.3 |
| 期間 | 実窓（5h / 7d = 解除時刻 − 長さ）と暦（日・週・月）。ccusage 式の推定ブロックは使わない | §3.4 |
| 見せる場所 | 右パネルの新ビュー `usage` + ステータスバーの 5h / 7d から開く | §4.1 |
| CLI / MCP | CLI は `tako usage`。MCP は**既存の `tako_sessions` に `action: "usage"`**（+506 バイト。新ツールは足さない） | §4.2 / §4.3 |
| 集計の持ち方 | `<data_dir>/usage/` の増分索引（ファイルごとの読み位置 + 5 分刻みの集約 + 写した鍵 + 制限の観測履歴）。起動時は読まない。初回の取り込みは背景で 1 回（実測: 4.2 GB を読んで assistant 行へ絞るまでで 37 秒） | §5 |
| 最初に入れるもの | **制限の観測の記録（S1）**。used_percent の履歴はこの機のどこにも残っておらず、後から遡れない | §1.2 |

### 1.2 利用制限の値（used_percent）

| 出どころ | 形 | 履歴 |
|---|---|---|
| tako mod の報告（`tako mod --json` の `panes[].report.rate_limits[]`） | `kind`（`five_hour` / `seven_day`）・`percent_used`（**値は整数**。f64 で届く）・`resets_at`・`observed_at`（mod が **% か解除時刻が変わったときだけ**打ち直す = 1% の段の時刻。`crates/tako-core/src/claude_mod.rs` の `ModRateLimit`） | **無い**。`ModHub.reports` はペインごとに最新の 1 件だけをメモリに持つ |
| Claude Code の statusLine の stdin（`rate_limits.five_hour.used_percentage` など） | 同上 | 無い（この機の statusLine は表示するだけで書き出さない） |
| ステータスバー（mod の無いペインは画面の読み取り。#1903） | 5h / 7d の % | 無い |
| codex の rollout（§1.5） | `token_count` ごとに `rate_limits` | **ある**（rollout そのものが履歴） |

- **used_percent の履歴は、この機のどこにも残っていなかった**。だから「後から遡って % を割り振る」はできず、
  観測を残し始めた時点から先しか % は出せない。これが S1 を最初に置く理由
- ただし `ModHub` に残っていた**古いペインの最終報告**は、それぞれ別の時刻の観測を持っていた。ログイン A の 7d で
  10 点（11% → 83%・3.4 日分）が取れたので、これを §2.1 の較正に使った
- 解除時刻は `13:20Z` / `15:40Z` / `13:00Z` / `22:00Z` のように**ちょうどの時刻とは限らない**（20 分刻みに見える）。
  ccusage の blocks は「最初の発言を時刻の頭へ切り捨てて 5 時間」と推定する（`rust/crates/ccusage/src/blocks.rs` の
  `floor_to_hour`）ので、実窓と最大 40 分ずれる（§3.4）

### 1.3 ログインと設定 dir

- この機の tako のアカウントは 4 つ（設定 dir が 4 つ）。`<設定 dir>/.claude.json` の `oauthAccount.accountUuid` を
  ハッシュして**一致だけ**を比べると、**3 つ（個人用 + 案件ごとに隔離した設定 dir 2 つ）が同じログイン A**、残り 1 つがログイン B だった
- 利用制限はログインごとにかかる（Anthropic の告知では Claude と Claude Code が 1 つの使用枠を共有する）。
  **tako のアカウントで束ねると、同じ枠を 3 回別々に数えてしまう**。束ねる鍵はログインにし、tako のアカウントはその下の段にする
- いまの `ModHub::account_rate_limits` は報告の `config_dir` で束ねている（`crates/tako-control/src/claude_mod.rs`）。
  帯・ステータスバーの用途では困らないが、usage 分析ではログインの鍵を別に持つ
- transcript の `bridge-session` 行に `ownerAccountUuid` がある。ただし Remote Control を有効にしたセッションにしか無く
  （10/09 以降の 1,633 本のうち 163 本）、その範囲では設定 dir とログインの対応に食い違いは無かった。ログインの鍵の主には使えない
- **既定の設定 dir の transcript には 2 通りのセッションが混ざりうる**: `CLAUDE_CONFIG_DIR` 無しで起動したもの（資格情報は
  `~/.claude.json`）と、`CLAUDE_CONFIG_DIR=~/.claude` で起動したもの（`~/.claude/.claude.json`）。どちらも `~/.claude/projects` へ
  書くので、**置き場だけではログインを決めきれない**（この機では今は 2 つとも同じログイン。accounts.yaml の説明には「`inherit` だと
  既定の `~/.claude.json` = 別のログインを拾う」とある）。mod の報告は `session_id` と `config_dir`（既定なら無し）を持つので、
  **報告が来たセッションはログインを確定できる**（§3.2・S1）

| 鍵 | 被覆 |
|---|---|
| cwd → projects.yaml（30 日） | **95.0%**。外れの大半（3.6%）はホーム dir で起動した master / solo（→ カタログの `profile` で拾える） |

| セッションカタログ（日別） | 10/08 以降は **94〜100%**、10/04 より前は **0〜20%**（500 件の上限で追い出された） |
| 直近 7 日 | カタログに載る 99.6%（worker 87.4%・master 12.2%）。**worker の使用量の 88.0% が ledger の task_type まで辿れた**。Issue は**ラベルに書いた順で最初の `#N`** で 85.5% に付いた（ledger の `issue` は下の不具合で使えない） |
| レジストリから消えた worker を ledger へ（ラベル・プロジェクト・開始時刻 10 分以内で後付け） | 216 件中 69 件（32%）しか当たらない → 後付けではなく spawn の時点で `ledger_id` をカタログへ持たせる（§3.2） |

- **ledger の `issue` は「その worker の Issue」ではない（不具合）**: `extract_issues`（`crates/tako-control/src/sessions.rs`）は
  ラベルとプロンプトから拾った番号を `sort_unstable()` で昇順に並べ、spawn の dispatch はその先頭 = **最小の番号**を ledger へ
  記録する。プロンプトは前例や規約の Issue に触れるので、直近 7 日でラベルに番号のある 176 件中 **170 件（97%）がラベルの最初の
  番号と食い違った**（この S0 自身も、前例として触れたエピックの番号で記録されていた）。カタログ・レジストリの `issues` も同じ
  関数の結果（並べ替え済みの全部。1 本の worker で 8 個など）なので、どれが主かは分からない
- 機能の鍵は**ラベルに書いた順で最初の `#N`** にする。直近 7 日の worker の使用量の 85.5% に付き、Issue は 172 件・上位 10 件で
  15%・上位 20 件で 26%（最大の 1 件で 2%）。ledger の `issue` で数えると小さい番号へ寄せ集められて 92 件・上位 10 件で 48% に
  なり、実態と違って見える
- この不具合は usage 分析と独立に直せる（spawn の記録に「主 Issue」= ラベルの最初の番号を持たせ、ledger の `issue` も同じ値にする。
  §9 の S2 に含めるか、先に別の Issue で直す）
- **#2199 で直した**: `extract_issues` は書いた順（重複は最初の出現だけ）で返し、spawn は `spawn_issues`（ラベル → プロンプトの順）で
  1 回だけ拾って、ledger の `issue` = その先頭、カタログ・レジストリの `issues` = 同じ並びを書く（先頭 = 主 Issue）。フィールドは
  増やしていない（移行なし）。**修正前の記録は書き換えない**（ledger は最小の番号・`issues` は昇順のまま）ので、過去分は S2 が
  ラベルから引き直す。A/B は `TAKO_2199_LEGACY=1`（昇順へ戻す）、実経路は `scripts/test-ledger-primary-issue-2199.sh`

### 1.5 codex と agy

- **codex**: `$CODEX_HOME/sessions/**/rollout-*.jsonl` の `event_msg` / `payload.type == "token_count"` に
  `info.total_token_usage`（累積。`input_tokens` / `cached_input_tokens` / `cache_write_input_tokens` / `output_tokens` /
  `reasoning_output_tokens`）・`info.last_token_usage` と、**`rate_limits`（`primary` / `secondary` の `used_percent`・
  `window_minutes`・`resets_at`・`plan_type`）が毎回載る**。`turn_context` に `cwd` / `model` / `effort`、`session_meta` に
  `git.branch` / `repository_url`。**使用量と観測が同じファイルに揃う**ので、claude と違って過去へ遡って % を割り振れる
  （tako は `codex_session.rs` で既に `rate_limits` を読んでいる = #985）。この機では 264 本・631 MB（最後の使用は 9/16）
- codex の累積値はサブエージェントの rollout で親の履歴を写すことがあり、ccusage は「最後に引き継いだ値を基準に、
  子のターンで増えた分だけ数える」と書いている（`docs/guide/codex/index.md`）。S5 で同じ扱いにする
- **agy**: 会話は `~/.gemini/antigravity-cli/conversations/<id>.db`（SQLite）。ccusage は `gen_metadata` の行（protobuf）から
  トークンを読んでいる（`docs/guide/antigravity/index.md`）。tako は SQLite の依存を持たない（#984 の判断）。
  実況 JSONL にトークン数は無い（MATRIX の注記・#1033）。**利用制限は前払いのクレジットで、5h / 週の窓が無い**（#985）

### 1.6 世間の算定方法と Anthropic の告知

| 方式 | 中身 | 出典 |
|---|---|---|
| ccusage | transcript の assistant 行を `message.id` + `requestId` で重複除去し、トークン（キャッシュ込みの総量）と LiteLLM 等の単価による費用を日・週・月・セッション・5 時間ブロックで集計。ブロックは「最初の発言を時刻の頭へ切り捨てて 5 時間」。上限は `--token-limit max`（過去の最大ブロック）で推定。used_percent は見ない | `docs/guide/blocks-reports.md` / `docs/guide/cost-modes.md` / `rust/crates/ccusage/src/blocks.rs` |
| Claude-Code-Usage-Monitor（v4） | statusLine のフックで Claude Code の**公式の `rate_limits` を取り込み、新しいうちはそれを正**にする。古い・切れたら、プランの固定上限（Pro 19k / Max5 88k / Max20 220k トークン）か過去ブロックの **P90** による推定へ落とし、数値に出どころの印（`official` / `local_estimate` / `experimental` / `unknown`）を付ける。7d の % は公式値だけで出す。履歴は任意の warehouse に source / account / project / model / day で残し、30 日の削除を越えて保持（既定 365 日） | README の「Key Features」「Persistent Usage Warehouse」「Token Limits by Plan」 |
| Anthropic | Pro / Max の Claude と Claude Code は 1 つの使用枠を共有する。重いモデルほど速く減る。**2026-03-26 以降、平日の混雑時間帯（太平洋時間 5〜11 時）は 5h 枠が速く減る**（週の枠は変わらない） | support.anthropic.com の Max プランの記事 / 2026-03 の報道（TechRadar・PCWorld） |

- ccusage は上限を推定して割る方式、Claude-Code-Usage-Monitor は**公式の % を正にして推定には印を付ける**方式。tako は
  tako mod の報告で同じ公式の値をペインごとに既に受けているので、Monitor と同じく公式値を正にできる。Monitor の README には
  **観測した % をプロジェクト・Issue へ配る（按分する）仕組みは書かれていない**ので、そこが tako の足す部分になる（§2）。
  「推定」の印（§2.4）と 30 日を越える保持（§5.2）は Monitor の作りに揃える
- 混雑時間帯の告知どおりなら、5h の「1% あたりの量」は時間帯で変わり、**固定の換算係数で 5h の % を予測する方式は
  原理的にずれる**（ただし §2.1 の実測では、12:00Z の前後で差は見えなかった）

## 2. 「利用制限をどれだけ使ったか」の推定

### 2.1 較正の実測

#### ログイン A の 7d（窓の開始 = 解除時刻 − 7 日。観測 10 点・3.4 日分）

観測点の間の区間ごとに「Δ 使用量 / Δ%」を出した。値は 10/15 以降の区間の中央値を 1.00 とした比（実額は API 換算で
1% あたり数十ドル・生トークンで 1% あたり約 1 億の桁）。

| 区間（UTC） | Δ% | API 換算 / 1% | 生トークン / 1% |
|---|---|---|---|
| 窓の開始 → 10/13 02:02 | 11 | 0.44 | 0.38 |
| 10/13 04:44 → 10/14 02:41 | 6 | 0.49 | 0.35 |
| 10/14 02:41 → 10/15 12:38 | 20 | **2.04** | **2.19** |
| 10/15 12:38 → 10/16 01:54 | 22 | 1.00 | 1.00 |
| 10/16 01:54 → 05:40 | 8 | 1.06 | 1.01 |
| 10/16 05:56 → 06:50 | 4 | 0.99 | 0.93 |
| 10/16 06:50 → 08:10 | 4 | 0.76 | 0.79 |
| 10/16 08:10 → 11:39 | 6 | 1.05 | 1.06 |

重みごとの「1% あたりの量」の変動係数（Δ% ≥ 4 の区間）:

| 重み | 全区間（7 区間） | 10/15 以降（5 区間） |
|---|---|---|
| 生トークン総量（キャッシュ読み出し込み。ccusage の Total） | 0.49 | **0.10** |
| API 換算 | 0.42 | **0.11** |
| 出力だけ | 0.36 | 0.16 |
| 入力 + 出力 | 0.36 | 0.16 |
| キャッシュ読み出しを除く（入力 + 出力 + 作成） | 0.34 | 0.21 |
| キャッシュ作成だけ | 0.34 | 0.23 |

読み取れること:

- **10/15 以降は 1% あたりの量がよく揃う**（API 換算・生トークンとも変動係数 0.1 前後）。この範囲では「使用量 ÷ 係数」でも
  ±10〜20% で当たる
- **ところが 1 日単位で係数が 0.44〜2.04 倍まで動いた区間がある**。モデルの内訳はどの区間もほぼ Opus 5.5 だけで、
  モデル差では説明できない。候補は (1) tako の外の使用（claude.ai・別の PC。同じ枠を共有する = §1.6）が週の前半に多かった、
  (2) 一時的に設定 dir とログインの対応がずれていた（`inherit` の起動が別のログインの資格情報を拾う注意が accounts.yaml の
  説明にある）。どちらも transcript からは確かめられない（§10）
- **固定の係数で % を出すと、この窓では最大 12 ポイントずれる**（後半の係数を窓全体に当てると、週の前半は −6〜−10 pt、
  10/15 以降は +11〜+12 pt）。区間按分（§2.2 の A）なら、どの区間でも観測した Δ% をそのまま配るので合計は崩れない
- この窓に区間按分を当てると合計 83.1%（観測 83%）・未分類 0.4%。**窓全体の比で配った場合と比べて、最大のプロジェクトで
  8.7 ポイント**（P1: 区間按分 30.9% / 全体の比 39.6%）違った。P1 の使用が 1% あたりの量の多い区間に偏っていたため

#### ログイン B の 5h（観測を 60 秒ごとに採取）

本番の `tako mod --json` を 60 秒ごとに読み取り（読むだけ。書き込みも操作もしない）、各ペインの `rate_limits` を採った。
窓（08:20〜13:20Z）の 12:02〜13:17Z に 14% → 29% の 16 点。窓の開始から各観測までの累積を、原点を通る比例で当てた誤差:

| 重み | RMSE | 最大誤差 |
|---|---|---|
| **API 換算** | **0.15 pt** | **0.2 pt** |
| 生トークン総量 | 0.42 pt | 1.0 pt |
| キャッシュ読み出しを除く | 0.48 pt | 1.2 pt |
| 出力だけ | 1.17 pt | 2.3 pt |

- API 換算は 1% の段の量子化（±0.5 pt）の中に収まり、生トークン総量の 3 分の 1 の誤差だった。**1 つの 5h 窓の中では
  1% あたりの API 換算はほぼ一定**（最初の 8 点だけでは API 換算 0.11・生トークン 0.20 pt で差が小さかったが、点を倍にすると開いた）
- 同じログインの 7d（10/15 22:00Z 開始）の 3 点（12% → 14%）でも API 換算が RMSE 0.06 pt（生トークン 0.11 pt）
- **窓の切り替えを観測した**: 旧窓は 13:17Z の 29% が最後で、13:24Z に解除時刻 18:20Z（= 13:20 + 5h）の新しい窓が 0%、
  13:29Z に 1% で現れた。使用が途切れずに続くと、新しい窓は旧窓の解除時刻ちょうどから始まる
- 窓の開始を「解除時刻 − 5h」（08:20Z）から後ろへずらすと、08:40 で RMSE 0.34・09:20 で 0.64 pt と悪くなる。前へずらした
  07:20 は 0.13 pt で差が無く、前側は区別できない（08:00〜08:20 は使用が無く、07 時台の使用は窓全体の約 2%）。上の窓の切り替えの
  観測と合わせて、§2.4 の「窓の開始 = 解除時刻 − 長さ」を採る。ccusage の時刻の頭への切り捨てなら、この窓は 08:00 開始・
  13:00 解除になり、実際の解除（13:20）と 20 分ずれる
- 混雑時間帯（太平洋時間 5 時 = 12:00Z）の前後で、1% あたりの API 換算は **1.00 : 1.01**（窓の開始〜12:02 は使用の 95% が
  12:00Z より前、12:02〜13:17 はすべて後）。告知の「混雑時間帯は 5h が速く減る」は、このログインのこの日には見えなかった
- 5h の 1% は、同じログインの 7d の 1% の約 6 分の 1（B の 7d は 3 点）。ログイン A は約 4 分の 1（A の 5h は 2 点だけ）。
  窓の大きさの比はプランで違う

### 2.2 比較と決定

| 方式 | 中身 | トレードオフ |
|---|---|---|
| **A. 区間按分（推奨）** | ログインと枠（5h / 7d）ごとの観測の列で、隣り合う観測の間の Δ% を、その区間に同じログインで使われたローカルの使用量の比でキーへ配る | 合計が観測と必ず一致し、混雑時間帯・プロモーション・プランの変更・重みの不確かさに引きずられない。観測が無い期間は出せない（→ B で補う） |
| B. 換算係数で割る | 「1% あたりの量」を推定し（ccusage の `-t max`、Usage-Monitor の P90 と同系）、使用量 ÷ 係数で % にする | 観測が無くても出せるが、§2.1 で係数が区間ごとに 0.44〜2.04 倍動いた。**観測の無い期間の推定にだけ使い、「推定」と明示する**（係数は直近 7 日の区間の中央値。Monitor v4 も公式値が古いときだけ推定へ落ち、印を付ける） |
| C. % を出さない | トークンと API 換算だけを見せる（ccusage の daily / session と同じ） | 依頼の「利用制限をどのくらい持っていかれたか」に答えられない。量の表示としては A と並べて出す |
| D. 公式の集計 API | サブスクリプションのログインの 5h / 7d の % を返す公開の API は見当たらない（Admin API の Usage and Cost は API 組織の従量課金の集計。出口は Claude Code の `/usage` の画面と mod / statusLine の `rate_limits` だけ） | 使えない |

**決定: A を主、B を観測の無い期間の補い**。根拠は「観測を正にする」= ずれの原因が分からなくても合計が崩れないこと。

### 2.3 按分の重み

| 重み | 中身 | トレードオフ |
|---|---|---|
| **API 換算（推奨）** | モデル別単価 × 5 成分（入力・出力・キャッシュ作成 5 分 / 1 時間・キャッシュ読み出し）。fast は 2 倍 | ログイン B の 5h（16 点）で最良（RMSE 0.15 pt。生トークンは 0.42、読み出し除外は 0.48）、B の 7d・ログイン A の 7d の後半でも最良級。モデル差（Haiku 5.5 は Opus 5.5 の 40 分の 1 の単価。Anthropic も「重いモデルほど速く減る」）を表せる。ccusage の費用と同じ定義なので利用者が照合できる。単価表の保守が要る |
| 生トークン総量 | 5 成分の単純和（ccusage の Total Tokens） | A の 7d の後半では変動係数 0.10 で同等だが、B の 5h では誤差が API 換算の 3 倍。またキャッシュ読み出しが 98% を占めるので、実質「読み出し量の比」になり、モデル差を表せない（Haiku のトークンも Opus と同じ重み） |
| キャッシュ読み出しを除く | 入力 + 出力 + 作成 | A の 7d の全区間では 0.34 と最良だが、後半は 0.21・B の 5h は 0.48 pt と悪い。読み出しが枠に効かないという根拠は無い |
| 成分ごとの回帰 | 区間の Δ% を 5 成分で回帰した係数 | 理想だが、今のデータは Opus 5.5 の読み出しが主で成分比がほぼ一定のため、係数が決まらない |

**決定: API 換算**。ログイン B の 5h では生トークン総量の 3 分の 1 の誤差だった（RMSE 0.15 / 0.42 pt）。
ログイン A の 7d では区別できなかった（どちらも Opus 5.5 の読み出しが主のデータ）。ほかの決め手は
「モデル差を表せること」と「既存ツールと照合できること」。S3 は区間ごとの当てはまり（変動係数）を記録し、モデルが混ざった
データが溜まったら成分ごとの回帰で見直す（§10）。

単価表（100 万トークンあたり USD。claude-api のリファレンス 2026-10-06 版。読み出しの倍率がモデルで違うことに注意）:

| モデル | 入力 | 出力 | 作成 5 分（×1.25） | 作成 1 時間（×2） | 読み出し |
|---|---|---|---|---|---|
| claude-opus-5-5 | 4 | 20 | 5 | 8 | 0.20（×0.05） |
| claude-opus-5 | 5 | 25 | 6.25 | 10 | 0.5（×0.1） |
| claude-fable-5-1 | 10 | 50 | 12.5 | 20 | 0.25（×0.025） |
| claude-fable-5 | 10 | 50 | 12.5 | 20 | 1.0（×0.1） |
| claude-haiku-5-5 | 0.10 | 0.50 | 0.125 | 0.2 | 0.01（×0.1） |
| claude-haiku-4-5 | 1 | 5 | 1.25 | 2 | 0.1（×0.1） |

- 表は `tako-core` に 1 か所で持つ。**索引に現れたモデルで表に無いものは API 換算を 0 にせず「単価不明」として別に数え**、
  `tako usage` の注記で気づけるようにする（S2 の受け入れ条件 5）。按分ではその区間の生トークン総量の比で代わりに配る
- 表示では API 換算に必ず「API 換算」と添える（サブスクリプションの請求額ではない）

### 2.4 区間按分の手順

ログイン `L`・枠 `k`（5h / 7d）ごとに:

1. 観測の列 `(t_i, p_i, r_i)` を作る（`t` = `observed_at`、`p` = %、`r` = 解除時刻）。複数のペインが同じログインを報告するので、
   `(r, p)` の組で重複を除き、同じ `r` の中で `p` は単調非減少にそろえる（下がった値は古い報告として捨てる）
2. 窓の開始 `s = r − 長さ` を `(s, 0)` の点として列の先頭に置く（窓が変わったら列を切る）
3. 隣り合う点の区間 `(t_{i−1}, t_i]` について、ログイン `L` の 5 分刻みの集約から区間に重なる分（端の刻みは重なった時間の比）を
   キーごとに足し、Δ = `p_i − p_{i−1}` をその比で配る
4. 区間のローカルの使用量が 0 で Δ > 0 なら、Δ は「**tako の外**」（claude.ai・別の PC・tako が読めない設定 dir）へ入れる
5. 最後の観測より後の使用量（今まさに使っている分）は、直近 7 日の係数で割った値を「推定」として出す
6. 観測が 1 点も無い窓（tako の外で使った・観測を始める前）は、窓ごと B の推定にする

- 1% の段で観測するので、1 区間の誤差は高々 1 ポイントで、区間をまたいで**足し合わせても積み上がらない**（差分の和が端の値に
  一致する）
- mod の報告は最大 15 秒の heartbeat と 1 秒の flush で届き、usage の行の時刻は応答の時刻。ずれは 5 分刻みの粒度に収まる
- 5h と 7d は別々に配る（同じ使用量が両方の枠を減らす）。画面は「7d の何 %」を主にし、5h は今の窓だけを出す

## 3. 帰属の鍵と粒度

### 3.1 階層

```text
ログイン（利用制限の単位）
 └ tako のアカウント（設定 dir）
    └ プロジェクト（projects.yaml のキー / master はプロファイル）
       └ 機能 = Issue（+ task_type）
          └ セッション（master / worker / solo）
             └ モデル
```

日・週・月と実窓（5h / 7d）は、この木のどの段にも掛けられる軸として持つ。

### 3.2 鍵の決め方

| 鍵 | 決め方（上から順に、最初に決まったもの） | 被覆（§1.4） |
|---|---|---|
| ログイン | 資格情報のファイル（`CLAUDE_CONFIG_DIR` があれば `<それ>/.claude.json`、無ければ `~/.claude.json`）の `oauthAccount.accountUuid` を `<data_dir>/machine_id` で塩付けしたハッシュ（12 桁）。どの資格情報で起動したかは ① mod の報告（`session_id` + `config_dir`）で確定 ② 無ければ transcript の置き場から推す（既定の設定 dir は `~/.claude.json` 側とみなす）。読めなければ設定 dir そのもの | 全件（①は mod の報告が来たセッション） |
| tako のアカウント | accounts.yaml の `config_dir` と transcript の置き場の一致。どれにも当たらなければ設定 dir の名前 | 全件 |
| プロジェクト | ① カタログの `project`（worker）② カタログの `profile`（master。「プロファイル: X」として出す）③ cwd の最長前方一致（`<project>-wt-N` は元のプロジェクトへ寄せる）④ 「未分類」 | 30 日で 95.0%（cwd だけ）、直近 7 日はカタログで 99.6% |
| Issue | ① spawn の記録の主 Issue（S2 で足す。ラベルに書いた順で最初の `#N`）② カタログの `label` の最初の `#N`（書いた順で読む。`issues` は並べ替え済みなので使わない）③ 無し。**ledger の `issue` は使わない**（§1.4 の不具合） | 直近 7 日の worker で 85.5% |
| task_type | ① カタログの `ledger_id`（S2 で足す）→ ledger の `task_type` ② レジストリの `ledger_id` → ledger の `task_type`（spawn の引数そのままなので正しい） | 直近 7 日の worker で 88.0% |
| 役割 | カタログの `kind`。無ければ「手動」 | 直近 7 日で 99.6% |
| gitBranch | **鍵にしない**。セッションの詳細に参考として出すだけ | Issue 形は 3.2% |

**決定（機能の鍵）**:

| 案 | トレードオフ |
|---|---|
| **A. tako の spawn の記録（ラベル・ledger / レジストリ / カタログ）を session_id で結ぶ（推奨）** | 直近 7 日で worker の 85.5% に Issue が付く。tako の外で起動した claude には付かない（→ プロジェクトまでは cwd で付く） |
| B. gitBranch | 3.2% しか付かない（§1.4） |
| C. cwd の worktree 名 | 0.1% |
| D. 会話の本文から推定 | **本文を読まない約束に反する**ので採らない |

- **カタログと `PendingSpawn` に `ledger_id` と主 Issue（`primary_issue` = ラベルに書いた順で最初の `#N`）を足す**（spawn の
  dispatch は ledger を書いた直後に id を持っている = `crates/tako-control/src/dispatch.rs` の `record_spawn` の並び。カタログの
  記録を ledger の後へ回すか、後から書き足す）。ledger の `issue` にも同じ主 Issue を入れて §1.4 の不具合を直す。
  serde の default で旧ファイルはそのまま読めるので移行は要らないが、`migration_registry` の指紋が変わる（PR で明示する）
- ラベルに番号が複数ある（不具合を束ねた worker の `#A / #B / #C: …` など）ときは最初の 1 つへ寄せる。分けて見たい需要が
  出たら S3 で「ラベルの番号で均等割り」を選べるようにする
- ledger にも `session_id` を持たせる案はあるが、ledger の記録は session_id の検出より前なので書き足しの経路が増える。
  カタログ側に `ledger_id` を持たせれば片方向で足りる

### 3.3 鍵は取り込んだ時点で写す

- カタログは 500 件・レジストリは 200 件で古いものから消え、transcript も 30 日で消える。**問い合わせの時に結ぶと、
  2 週間前の使用量は鍵を失う**（§1.4 の日別の被覆）
- 索引は使用量を取り込むとき、そのセッションの鍵（§3.2 の決め方の結果）を `sessions.jsonl` に写して持ち続ける。
  後からカタログに `project` が付いた（pending からの昇格）などで鍵が良くなったら上書きする（悪くはしない = 未分類で上書きしない）
- 写すのは鍵と `label`（tako 自身のメタデータ）まで。`prompt_head` は写さない

### 3.4 期間

| 案 | トレードオフ |
|---|---|
| **A. 実窓（5h / 7d = 観測した解除時刻 − 長さ）+ 暦（日・週・月。ローカル時刻）（推奨）** | 「今の窓で何 % を持っていかれたか」に正確に答えられ、暦で振り返れる。実窓は観測が要る（無い窓は B の推定） |
| B. ccusage 式の推定ブロック（最初の発言を時刻の頭へ切り捨てて 5 時間） | 観測が無くても切れるが、実際の解除時刻は 20 分刻み（§1.2）で最大 40 分ずれる（§2.1 の B の 5h では 20 分ずれた）。7d には使えない |
| C. 暦だけ | 単純だが、利用制限の窓と合わない |

**決定: A**。既定の期間は「今の 7d の窓」（週の枠が一番効くため。#2192 の依頼の「どのくらい持ってかれてるか」）。

### 4.3 MCP

|---|---|---|
| **A. 既存の `tako_sessions` に `action: "usage"` と引数 `by` / `window` / `account` を足す（推奨）** | **+506 バイト**（説明 140・enum 8・引数 3 つ 358）→ 203,595 / 204,800 | 会話の索引という同じ対象で、`project` / `role` / `id` / `limit` をそのまま使える。`tako_sessions` の説明が長くなる |

`tako_core::usage`（純関数）→ `tako_control::usage`（索引の読み書き）へ渡す 1 本で、CLI `tako usage` も同じ要求を出す。

## 5. 集計の持ち方と負荷

### 5.1 比較

| 案 | トレードオフ |
|---|---|
| **A. 増分の索引（推奨）** | ファイルごとの読み位置を覚え、追記された分だけ読む。問い合わせは小さな集約を読むだけ。読み位置の管理（切り詰め・削除・同じ id の差し替え）が要る |
| B. 問い合わせのたびに全走査（ccusage の方式） | 実装は単純だが、この機で 4.2 GB を読む（jq で 71.6 秒・`cat` + `grep -F` で絞るだけでも 37 秒）。対話には遅い |
| C. mod の `turn.complete.usage` を受けて記録する（push） | 追加の読み込みが要らないが、mod の効いていないペイン・tako の外の claude・過去の分を拾えない |
| D. SQLite 等の DB に入れる | 集計が楽だが新しい依存が要り、量（5 分刻みで 30 日 13,197 行）に見合わない |

**決定: A**。C は S1 の観測の記録には使う（mod の報告に乗る）が、使用量の正本は transcript にする。

### 5.2 索引の形（`<data_dir>/usage/`）

| ファイル | 中身 | 大きさの見込み |
|---|---|---|
| `cursor.json` | transcript ごとの `dev` / `ino` / `size` / 読んだバイト位置 / 最後の `message.id` とその時点で数えた 5 成分 | ファイル数（3,700）× 約 150 バイト |
| `buckets/<YYYY-MM>.jsonl` | 5 分刻み × セッション × モデルの 5 成分と API 換算（マイクロドル）。追記のみで、読むときに同じ鍵を足し合わせる | 30 日で 13,197 行（この機）≒ 2 MB |
| `sessions.jsonl` | session_id → ログイン・アカウント・agent・役割・プロジェクト・プロファイル・Issue・task_type・ledger_id・label・最初 / 最後の時刻（§3.3） | 保持中の transcript で 2,272 セッション |
| `limits.jsonl` | ログイン・枠・解除時刻・%・`observed_at`・出どころ（`mod` / `codex` / `screen`）。値が変わったときだけ追記 | 1 日に数百行 |

- 同じ id の行は連続するので（§1.1）、増分の読み手は「そのファイルの最後の id と数えた値」だけ覚えればよい。続きの行で
  output が増えていたら差分だけを足す
- ファイルが縮んだ・`ino` が変わったら最初から読み直す（その transcript の分は `message.id` で数え直し済みを除く）
- transcript が消えても集約は残す。**保持は 365 日**（Claude-Code-Usage-Monitor の warehouse の既定と同じ）、35 日より古い刻みは月替わりに日単位へまとめる（S2 の判断点）
- 書き込みは追記（`buckets` / `limits`）と config_io の排他 + アトミック書き換え（`cursor` / `sessions`）
- 新しい永続ファイルなので、`migration_registry` の指紋に登録し、置き場は設定共有のカタログ（#513 の許可リスト）に
  `Class::Local` で載せる（載せないと `catalog_coverage` が落ちる = 共有されない側に倒れる）

### 5.3 負荷

| 場面 | 実測・見込み |
|---|---|
| 初回の取り込み（4.2 GB） | 部分一致（`"type":"assistant"`）で絞ると、パースが要るのは 250,547 行・876 MB（全体の約 21%）。`cat` + `grep -F` で 4.2 GB を読んで絞るまでが 37 秒（ページキャッシュの温まり具合は見ていない。I/O と部分一致の内訳も未測定）。Rust の JSON パースはこの 876 MB に数秒の見込み（未測定）。**背景のスレッドで 1 回だけ**、ファイルごとに区切って進み、メモリ圧が高いときは止まる（#1994 の判定を使う） |
| 平常時 | 60 秒ごとに追記分だけ読む。追記の量は平均で 1 分あたり約 100 KB（4.2 GB / 30 日） |
| 起動時 | **何も読まない**。最初の更新は起動から 60 秒後。索引は問い合わせ（ビュー・CLI・MCP）で初めて読み込む |
| 常駐のメモリ | 直近 7 日の集約だけを持つ（数千行 = 1 MB 前後）。それより前は問い合わせのたびにファイルから読む |
| CLI の `--rebuild`（索引の作り直し） | 重い処理なので `tako queue` を通す |

## 6. プライバシー

- **本文を読まない・残さない**: 索引の読み手は assistant 行のうち §1.1 の表のキーだけを持つ構造体へ読む（serde は他のキーを
  捨てる）。索引のどのファイルにも `content` / `text` / `prompt` 系のキーを持たせない。番犬: 偽の transcript の本文に印の文字列を
  入れて取り込み、`<data_dir>/usage/` のどこにも印が出ないこと・索引の構造体に本文系のフィールド名が無いこと
- **診断ログ**（persist.log / perf.log / stderr）には件数・所要・バイト数だけを出し、cwd・label・Issue 番号・トークン数の
  内訳を出さない（AGENTS.md の絶対ルールの延長）
- ログインの鍵は塩付きハッシュだけを持ち、`accountUuid` もメールアドレスも保存しない・表示しない。画面では tako のアカウント名と
  「ログイン A」形式の短い名前（利用者が変えられる）で出す
- 置き場は `<data_dir>` の中だけ。設定共有（`tako config`）には載せない（`Class::Local`）
- スマホ（PWA）に出すのは別スライスで、権限（#1452）の段を決めてから（プロジェクト名・Issue が見えるため）

## 8. 判断点と推奨（まとめ）

| 判断点 | 推奨 | 根拠（1 行） | 他案のトレードオフ |

依存:


### S1 制限の観測を残す + ログインの鍵

- やること: `ModHub` が報告を受けるたび、ログイン × 枠の `(解除時刻, %)` が前回と違えば `limits.jsonl` へ 1 行追記
  （`observed_at`・`source: mod`）。mod の無いペインでステータスバーが画面から読んだ値は `source: screen` で追記（按分では mod を優先）。
  ログインの鍵（§3.2）と、報告の `session_id` → ログインの対応（`sessions.jsonl` の最初の列。S2 が使用量の帰属に使う）。
  置き場 `<data_dir>/usage/` の作成・設定共有のカタログへ `Local` で登録・`migration_registry` の指紋。
  `tako usage`（この段では観測の履歴の要約だけ = ログインごとの最新の % と観測の点数）と MCP `tako_sessions` `action: "usage"`
- 受け入れ条件:
  1. 隔離 GUI で `tako mod report` に偽の報告を流し、% か解除時刻が変わったときだけ 1 行増える（同じ値の heartbeat では増えない）
  2. 同じログインの 2 つの設定 dir が同じ鍵になり、別のログインは別の鍵になる。既定の設定 dir で `CLAUDE_CONFIG_DIR` 無し / `=~/.claude` の 2 本の偽セッションが、資格情報のファイルの違いどおりに別の鍵へ入る。`.claude.json` が無い・読めないときは設定 dir の鍵へ落ちる
  3. 鍵とファイルに `accountUuid` の生の値が出ない（番犬）。診断ログに cwd・label が出ない
  4. 起動時に `limits.jsonl` を読まない（最初の追記で開く）。`catalog_coverage` / `migration_registry` / `mcp_catalog_snapshot` が緑で、増分のバイト数を PR に書く
  5. A/B: `TAKO_2192_S1_LEGACY=1` で記録しない
- 依存: なし

### S2 使用量の索引（claude）+ `tako usage`（量だけ）

- やること: §5.2 の `cursor` / `buckets` / `sessions` と増分の読み手（§1.1 の分割行・仮の output・`<synthetic>`・サブエージェント・
  ファイルの縮み / 消失）、取り込み時の鍵の写し（§3.2 / §3.3）、カタログと `PendingSpawn` の `ledger_id` / `primary_issue`、
  ledger の `issue` の不具合（最小の番号が入る。§1.4）の修正、単価表（§2.3）。
  `tako usage --by … --window …` はトークン（5 成分）・API 換算・セッション数を出す。MATRIX `usage_tokens`。
  ledger の不具合だけは先に別の Issue で直してもよい（直すまでの spawn も、カタログの `label` から主 Issue を引けるので失われない）
- 受け入れ条件:
  1. 偽の transcript（分割行・仮の output・`<synthetic>`・subagents・書きかけの最終行・切り詰め）で期待値どおり。2 回目の更新で読むバイトが追記分だけ
  2. この機の実データで、jq の参照集計（S0 で使った抽出 = 同じ定義）と API 換算・トークン数の合計が一致する（±0.1%）
  3. 本文の印が `<data_dir>/usage/` に出ない番犬。初回の取り込みの所要・ピークの RSS を PR に書く（背景で走り、UI が止まらない）
  4. カタログが追い出した後も、取り込み済みのセッションは鍵を保つ（500 件を超える合成カタログで確認）
  5. 表に無いモデルは「単価不明」として別に数え、注記が出る
  6. ラベル `#2192 …` でプロンプトにもっと小さい番号（`#322` 等）があっても、主 Issue と ledger の `issue` が 2192 になる（A/B）
- 依存: S1

### S3 区間按分（%）

- やること: §2.4 の手順を `tako_core::usage` の純関数で。`tako usage` に 5h / 7d の % 列・「tako の外」・「推定」・
  窓ごとの係数の幅（当てはまりの目安）。MATRIX `usage_limit_share`
- 受け入れ条件:
  1. 合成データ（既知の重み・混雑時間帯で係数を変えた列・観測の欠け・窓のまたぎ・古い値を持つペインの混在・Δ が下がる報告）で、
     合計が観測と一致し、キーごとの誤差が 1 ポイント以内
  2. この機の実データで、S0 の §2.1 の窓（ログイン A の 7d）に当てて合計が観測 ±1 ポイント
  3. ローカルの使用量が 0 の区間の Δ は「tako の外」へ入る。観測の無い窓は「推定」と明示される
- 依存: S1 / S2

### S4 右パネルの `usage` ビュー + ステータスバーからの導線

- 依存: S3

### S5 codex

## 10. 未検証・リスク

- **ログイン A の 7d で係数が 1 日単位で 0.44〜2.04 倍動いた原因は特定していない**（§2.1）。区間按分は合計を崩さないが、
  その区間の内訳（どのキーにどれだけ）は不確か。S3 で区間ごとの係数を記録し、外れた区間を画面で薄く出す
- 重みは B の 5h で API 換算が明らかに勝った（RMSE 0.15 / 0.42 pt）が、A の 7d では区別できない（どちらも Opus 5.5 の読み出しが
  主のデータ）。モデルが混ざったデータで回帰して見直す
- 混雑時間帯で 5h が速く減る件（告知 2026-03）は、ログイン B の 1 窓で 12:00Z の前後に差が見えなかっただけで、別のログイン・
  曜日・18:00Z 以降（混雑時間帯の外）は採っていない。区間按分は時間帯の差があっても合計を崩さない
- tako の外の使用（claude.ai・デスクトップ・スマホ・別の PC）は見えない。区間のローカルの使用量が 0 なら「tako の外」に出るが、
  ローカルとの混在は按分で薄まり、外の分として分けられない
- transcript を残さない claude の呼び出し（`claude -p` の一部・自動命名の haiku 等）は数えられない。隔離テストの一時 HOME の
  transcript も消える
- Claude Code の版で transcript の行の種類が増えている（`api-request` 系は今回の版で確認）。読み手はキー名で拾い、知らない
  キーは無視する。usage の形が変わったら S2 の参照集計との一致で気づける
- Windows の transcript の置き場（`%USERPROFILE%\.claude\projects`）と `.claude.json` は同じ形の見込みで、実機では未実測
- `cleanupPeriodDays` を短くしている利用者は、初回の取り込みで遡れる期間が短くなる（索引に入った後は 365 日残る）
- 単価はモデルの追加で古くなる（§2.3 の「単価不明」の扱い）
