## 1. モジュール配置

依存方向は既存どおり `tako-app(ui) → tako-control → tako-core`。**GPUI 依存は tako-app だけ**。

```
tako-core/src/lsp/          新設。プロセスも I/O も持たない純粋部分
  position.rs   UTF-8 バイト <-> UTF-16 コードユニットの相互変換（§4）
  servers.rs    サーバ検出表（§3）。言語追加 = この表への行追加
  root.rs       プロジェクトルート検出（§5）
  state.rs      ライフサイクルの状態機械（純粋な遷移関数。§6）

tako-control/src/lsp/       新設。プロセスと I/O。GPUI 非依存のまま
  rpc.rs        JSON-RPC のフレーミング + id 管理 + タイムアウト（§7）
  server.rs     1 サーバのプロセス管理（spawn / 3 スレッド / shutdown）
  manager.rs    複数サーバの束ね + 開いているドキュメントの登録簿（§8）
  diagnostics.rs 診断の受信と保持のみ（描かない。#1679 が読む）

tako-app/                   S1 では「起動のきっかけ」と status 表示だけ
  preview.rs / main.rs から manager を叩く。LSP の型を UI へ漏らさない
```

`manager` の実体は GUI プロセス（tako-app）が所有する。CLI / MCP は既存どおり IPC を通って
`dispatch` へ入り、`ControlHost` 経由で同じ manager を触る（**CLI と MCP は同じ 1 本を通す** =
`.agent/conventions.md`「CLI と MCP は『同じ 1 本』を通す（Issue #1453 / #1544）」）。

**新しいクレートは作らない。** tako-control は既に GPUI 非依存でプロセスと I/O を持つ層
（`ipc.rs` の accept スレッド・`remote` の daemon）なので、置き場としてそのまま成立する。

## 2. 並行モデル — スレッド + futures channel（tokio も GPUI executor も使わない）

Zed の LSP クライアントは GPUI の `BackgroundExecutor` 上の 3 タスクで動くが、**tako は
それを真似しない**。理由: tako-control を GPUI 非依存に保つ必要があり（依存方向の規約）、
かつ tako には**同じ形の前例が既にある**。

`.agent/architecture.md`「IPC トランスポート」節:

> accept スレッド + 接続毎スレッドのブロッキング IO で受け、リクエストは
> futures channel で UI スレッドへ渡して dispatch する（tokio を持ち込まない方針を維持）

S1 もこれに揃える。**1 サーバにつき 3 スレッド**（Zed の 3 タスクと同じ役割分担）:

| スレッド | 役割 | 詰まったときの振る舞い |
|---|---|---|
| reader | stdout から 1 メッセージずつ読む | 送り先の channel が満杯なら**読むのをやめる**（OS のパイプに背圧を掛け、メモリへ溜めない） |
| writer | 送信キューから取り出して stdin へ書く | サーバが読まなければブロックする（キューの上限で検知） |
| stderr | 1 行ずつ読む | 直近 N 行だけリングバッファに保つ（`tako lsp status` の診断用） |

UI スレッドへの受け渡しは `futures::channel::mpsc`。**bounded** にして上限を
**128 メッセージ**（Zed の `INCOMING_MESSAGE_QUEUE_CAPACITY` の実測値をそのまま初期値にする）。
UI が詰まっているときにメモリを無限に食わないための設計で、tako の #782 / #1001 と同じ問題意識。

大量の通知を受けたときに UI スレッドを飢えさせない配慮（Zed の `yield_now`）は、tako では
「UI スレッド側が 1 フレームで処理する件数に上限を置く」形で持つ（残りは次フレームへ繰り越す）。

## 3. サーバ検出表 — 言語追加は「行追加だけ」

ユーザー要望（#1007 コメント、2026-08-28）:

> ゆくゆくは HTML とかネット系の言語や java とかそこら辺とか，とにかく色々対応させたい

**第 2 波以降の追加コストがこの表の形で決まる。** `tako-core/src/lsp/servers.rs`:

```rust
pub struct ServerSpec {
    /// 安定 ID（設定ファイル・CLI の --name・MATRIX のキーに使う）
    pub id: &'static str,              // "rust-analyzer"
    pub language: &'static str,        // "rust"（LSP の languageId）
    pub extensions: &'static [&'static str],   // ["rs"]
    /// 実行ファイル名。解決は必ず platform::exe::find を通す
    pub program: &'static str,         // "rust-analyzer"
    pub args: &'static [&'static str], // []
    /// ルートの印。上へ辿って最初に見つかったものを rootUri にする
    pub root_markers: &'static [&'static str], // ["Cargo.toml"]
    /// 未導入のときに出す導入コマンド。日英の実文ではなく ui_text のキー
    pub install_hint_key: &'static str,
}

pub const SERVERS: &[ServerSpec] = &[ /* 段階 1 は 4 行 */ ];
```

段階 1 の 4 行（ユーザー確定の順。#1007 コメント）: **Rust（rust-analyzer） → C/C++（clangd）
→ TypeScript / JavaScript（typescript-language-server） → Python（pyright）**。
C/C++ が 2 番目なのは、ユーザー原文の「ヘッダ」が **C/C++ の `#include` ヘッダファイル**と
確定したため。

**表以外に言語名を書かない。** `if language == "rust"` のような分岐を散らすと、第 2 波の
追加が「行追加だけ」で済まなくなる。番犬でこれを止める（§12 の受け入れ条件）。

文言を表に直書きせず `install_hint_key` にするのは #435 / #920 の作法（日英の実文は
`ui_text` 側が持ち、テストに理由文を直書きしない）。tako-core は tako-app の `ui_text` に
依存できないので、**キーだけを表に置き、引くのは tako-app / tako-cli 側**。

## 4. UTF-8 <-> UTF-16 の変換（`tako-core/src/lsp/position.rs`）

LSP 3.17 の既定は **UTF-16 コードユニット**で、UTF-16 対応はサーバ側の必須要件。
`positionEncodings` で `utf-8` を交渉する余地はあるが、**Zed は UTF-16 だけを申告している**
（成熟した参照実装がその最適化を採っていない）ので、**UTF-16 変換層を最初から持つ**。

`TextBuffer` は全てを UTF-8 バイトオフセットで持つ（`text_edit.rs` の不変条件）。
入口を 2 本だけに閉じる:

```rust
/// UTF-8 バイト位置 -> LSP の (0 起点の行, UTF-16 桁)
pub fn lsp_position_of(text: &str, byte_offset: usize) -> (usize, usize);
/// LSP の (0 起点の行, UTF-16 桁) -> UTF-8 バイト位置
pub fn byte_offset_of_lsp_position(text: &str, line: usize, utf16_col: usize) -> usize;
```

既存の `TextBuffer::line_byte_col`（`text_edit.rs`）/ `offset_for_line_byte_col` と**同じ流儀**で
並べる。サロゲートペアが要点（絵文字 U+1F600 は UTF-16 で 2 コードユニット・UTF-8 で 4 バイト）。
`char::len_utf16()` を使う。

**境界の扱いを決めて固定する**: 行の途中で UTF-8 の境界に乗らない位置を渡されたら
**手前の境界へ丸める**（`text_edit.rs` の `snap_boundary` と同じ方針）。サロゲートペアの
片割れを指す UTF-16 桁も同じく手前へ丸める。CRLF の行末は `\r` の手前を行末とする（#1650 で
CRLF 保持が入っているので、`\r` を桁に数えない）。

テストは**日本語 / 絵文字 / タブ / CRLF / 行末 / 空行 / 空ファイル**で両方向を固定する（最低 12 ケース）。

## 5. プロジェクトルート検出（`tako-core/src/lsp/root.rs`）

ファイルのあるディレクトリから上へ辿り、`root_markers` の最初の 1 つが見つかった所。
見つからなければ **`git::repo_root(path)`**（`crates/tako-core/src/git.rs` に既存）、
それも無ければファイルの親ディレクトリ。

Rust の workspace のように印が入れ子になる場合は**最上位**を採る（`Cargo.toml` を見つけても
そこで止めず、上に `[workspace]` を持つ `Cargo.toml` があればそちらを採る）。
これは rust-analyzer の挙動に合わせるための例外で、**表の `root_markers` とは別の判定**に
なるので純粋関数として独立させ、テストで固定する。

**上へ辿る部分は `tako_core::project_root` を使う**（#1656 で Code Runner のプロジェクト既定と
共有する形で新設済み）。境界（HOME の段は見ない / `.git` の段で止まる / 深さ上限 32）は
そこが持つので、LSP 側で辿り方を書き直さない（印がファイル名で表せない探し方は `find_upward_map(start, bounds, probe)`）。git ルートのフォールバックも
`project_root::repo_root_within`（`git::repo_root` は git プロセスを起こすので、
ファイルを開くたびに走る経路には重い）。Rust の workspace の扱いだけは違う:
Code Runner は cargo と同じ「最初に見つかった `[workspace]`」を採るが、ここは
rust-analyzer に合わせて最上位を採る（1 段のワークスペースでは両者は一致する）。

`canonicalize` の結果を持ち回らない（`.agent/conventions.md`「Issue #970」）。
rootUri へ渡す前に `file_uri`（`crates/tako-core/src/file_uri.rs` に既存）で URI 化する。
Windows のドライブ文字・verbatim 表記の扱いは `platform::path::relative_under`（#1569 で新設）と
同じ流儀にする。

## 6. ライフサイクル（`tako-core/src/lsp/state.rs` + `tako-control/src/lsp/server.rs`）

```
[未起動] --(対象言語のファイルを編集モードで開く)--> [起動中]
[起動中] --(実行ファイルが無い)--> [未導入]（理由 + 次の一手を出す。#983）
[起動中] --(spawn 成功)--> [initialize 送信] --(応答)--> [initialized 通知] --> [稼働]
[稼働]   --(プロセス死亡)--> [クラッシュ] --(再起動 3 回まで)--> [起動中] / [諦めた]
[稼働]   --(最後のバッファを閉じた + 猶予 60 秒)--> [shutdown] --(応答 or 5 秒)--> [exit] --> [未起動]
```

遷移そのものは**純粋関数**（`state.rs`）にしてテストで固定し、プロセス操作は `server.rs` が持つ。

| 論点 | 決め | 根拠 |
|---|---|---|
| 実行ファイルの探索 | **`platform::exe::find(name)`（境界 B16）を必ず通す** | #898 / #877 で `which` 直叩きを全部ここへ寄せた。Windows は `PATHEXT` とユーザー導入先まで見る。#1372 で「起動できる形」だけを返すようになっている |
| 起動時の env | `platform::child_cmd`（境界 B21。`command()` / `user_env_cli`） | `.app` を Dock から起動すると PATH が最小構成になる。ログインシェル経由でないと Homebrew のサーバが見つからない |
| コンソール窓 | `platform::process::no_console_window` を通す | Windows で起動のたびに黒窓が明滅しない |
| 未導入のとき | **理由 + 次の一手 + 導入コマンド**（#983 の作法） | 無言で死なない。過去に踏んだ穴 |
| 孤児を残さない | 子の pid を持ち、Drop と GUI 終了経路の両方で kill。生死の判定は **`platform::process::pid_alive`（#1557 / #1581 の境界）** | tako は孤児プロセスで何度も事故っている |
| リクエストのタイムアウト | **120 秒**（Zed の実測値） | `.agent/conventions.md`「外部コマンドを待つときは上限を持つ（Issue #1503）」。無限に待たない |
| shutdown のタイムアウト | **5 秒**（Zed の実測値）。超えたら kill | 同上 |
| 再起動の上限 | **3 回**（指数バックオフ。上限に達したら「諦めた」で止まる） | #813 の「1 回の上限あたり 3 回で打ち切り」と同じ作法。無限再起動でマシンを焼かない |
| 起動のきっかけ | **編集モードに入ったとき**（ファイルを開いただけでは起こさない） | プレビューは閲覧が主で、全てのファイルでサーバを起こすとゼロコンフィグの軽さが壊れる。判断待ち §13-2 |
| アイドル時 | **何も投げない**。タイマーを持たない | #772 の作法。受け入れ条件で実測する |

## 7. JSON-RPC（`tako-control/src/lsp/rpc.rs`）

型は `lsp-types`（crates.io のデファクト。直近 DL 8,192,033）、配線は自作。
既製の JSON-RPC クレートも `async-lsp` も採らない（後者は既定 features に tokio が入る =
tako の「tokio を持ち込まない」方針と衝突する。詳細は §13-1）。

- 送信: `Content-Length: <len>\r\n\r\n<body>`。Zed の実装で 6 行、受信側も 50 行程度
- 受信: ヘッダを `\r\n\r\n` まで読み、`Content-Length` ぶんを `read_exact` して `serde_json`
- **分割受信に耐える**（1 メッセージが複数回の read に割れる / 1 回の read に複数メッセージが乗る）
- id は `enum RequestId { Int(i32), Str(String) }`。応答待ちのハンドラを id で引く
- タイムアウトで待ちを解いたら**ハンドラ表からも消す**（漏れを作らない）
- `$/cancelRequest` を送れる口を S1 で作る（使うのは #1682 の補完）
- サーバからの request（`window/showMessage` / `workspace/configuration` 等）は S1 では
  **既定の応答を返すだけ**。無視して黙らない（サーバが待ち続ける）

## 8. ドキュメント同期と版（`tako-control/src/lsp/manager.rs`）

- `didOpen`: 編集モードに入ったとき。`languageId` は検出表の `language`
- `didChange`: **incremental**。#1651 の `EditDelta`（範囲 + 置換後）を
  `TextDocumentContentChangeEvent { range, text }` へ写す。範囲は §4 の変換で UTF-16 桁へ
- `version`: **#1658 が返すドキュメントの版をそのまま使う**。LSP 用の版を別に作らない
  （2 種類あると必ず食い違う）
- `didClose`: 編集モードを抜けた / ペインを閉じた / ファイルが差し替わった
- 外部変更（#1659 / FR-3.15 のライブリロード）で全文が入れ替わったときは、
  incremental ではなく**全文の `didChange`**（範囲省略）を送る

**サーバが未起動・未導入でも編集経路が壊れないこと**が最優先（ゼロコンフィグ原則）。
同期は「サーバが稼働しているときだけ通る枝」にする。

## 9. 能力ネゴ

`initialize` のクライアント能力は**段階 1 で実際に使うものだけ**申告する
（使わない能力を申告するとサーバが無駄な仕事をする）。S1 では
`textDocument.synchronization`（incremental）と `textDocument.publishDiagnostics` のみ。
機能スライスが自分の能力を足していく。

`positionEncodings` は **UTF-16 のみ**を申告する（§13-3）。

応答の `ServerCapabilities` を保持し、`tako lsp status` で読めるようにする。
**上のスライスは「能力に無い機能を出さない」ためにここを読む**（#1684 の右クリックメニューが
最初の利用者）。

## 10. 診断の受信（`tako-control/src/lsp/diagnostics.rs`）

S1 は `publishDiagnostics` を**受けて保持するだけ**。描画（波線・右パネル）は #1679。
保持はファイル URI ごと。**ドキュメントを閉じたら捨てる**（#830 の「閉じたら解放」の作法）。
件数を数える口を用意し、#1679 の受け入れ条件（閉じたら 0）が測れるようにする。

## 11. ログ（ここだけ規約が厳しい）

AGENTS.md の絶対ルール: ペイン内容・送信テキスト・`TAKO_TOKEN` を診断ログへ出さない。
**LSP の I/O はソースコード本文をそのまま含む**ので、既定で本文を書いてはいけない。

| ログ | 既定 | 内容 |
|---|---|---|
| `perf.log` | ON | method 名・所要時間・結果の種別（成功 / タイムアウト / エラーコード）だけ |
| `persist.log` | ON | サーバの起動 / 終了 / クラッシュ / 再起動の回数。**本文は書かない** |
| `<data_dir>/lsp/<server id>.log` | **OFF** | `TAKO_LSP_DIAG=1` のときだけ。生の JSON-RPC を残す（デバッグ用） |

`tako lsp status` の応答に stderr の直近 N 行を載せるのは**診断として要る**が、
**ソースコード本文が stderr に出るサーバがありうる**ので、行数の上限と
「これは opt-in の診断出力」である旨を明記する。#927 の番犬
（`crates/tako-control/tests/no_personal_data.rs`）の対象はリポジトリのソースなので、
**テストの期待値へ実パスを焼き込まない**こと。

## 12. MCP / CLI の口

S1 で公開するのは**サーバのライフサイクルだけ**（言語機能は各スライスが足す）。

```
tako lsp status  [--name <server id>] [--json]   状態・能力・診断件数・stderr 直近
tako lsp servers                                  検出表と解決結果（導入済み / 未導入）
tako lsp restart [--name <server id>]             止めて起こし直す
```

MCP は **`action` 引数を持つ 1 ツール `tako_lsp_server`**（`status` / `list` / `start` /
`stop` / `restart` / `logs`）。ツールを 3 本増やさない（#513 / #919 と同じ作法。
カタログは 200 KB 以内 = #1540）。#322 の原則どおり、案内するコマンドは常に最簡形
（`tako lsp status`。`--name` は既定で全サーバ）。

T3（`crates/tako-cli/src/main.rs` の `mod platform_matrix_parity`）を通すため
`CLI_KEY_OVERRIDES` へ **`("lsp", "tako_lsp_server")`** を足す。
#1679 以降で言語機能の `tako_lsp` が入ったら、前方一致の最長勝ちを使って
`("lsp status", …)` / `("lsp servers", …)` / `("lsp restart", …)` を `tako_lsp_server` へ、
残りの `("lsp", "tako_lsp")` を言語機能へ振り直す。

`tako-core/src/platform/support.rs` の MATRIX へ 1 マス足す。**Windows で LSP サーバが動くかを
実測しないと `Supported` と言えない**（#591 の規約。過大申告は system prompt 経由で
エージェントを誤らせる）。S1 の段階では実測できたところまでを `windows_evidence` に書く。

## 13. テスト戦略 — 偽サーバ（stdio のモック）

実サーバ（rust-analyzer 等）は CI に入れられない（導入が重い・応答が環境依存）。
**2 段で測る**:

### (a) in-process（フレーミングと id 管理）

`rpc.rs` を `Read` / `Write` に対して書き、テストでは `Cursor` / パイプを渡す。
ここで固定するもの: ヘッダの組み立て / 分割受信 / 1 read に複数メッセージ / 不正 JSON /
id の引き当て / タイムアウトでハンドラ表から消えること。

### (b) 実プロセス（spawn・孤児・クラッシュ・再起動）

**テスト専用の偽サーバを Rust で書き、`tako-control` の `[[bin]]`（または `examples/`）として
ビルドする**。テストからは `env!("CARGO_BIN_EXE_<名前>")` で絶対パスが取れる
（Cargo 標準の仕組み。Windows でも同じ形で動く）。

偽サーバはシナリオを引数 / env で切り替える:

| シナリオ | 振る舞い | 測るもの |
|---|---|---|
| `normal` | 正常に握手して黙る | メッセージ列・アイドル時の無送信 |
| `slow` | initialize に応答しない | タイムアウトが効くこと |
| `crash` | 握手後に自分で落ちる | 再起動の上限 3 回・「諦めた」で止まること |
| `split-header` | `Content-Length` を 2 回に分けて書く | 分割受信 |
| `garbage` | 不正な JSON を混ぜる | 壊れたメッセージで死なないこと |
| `chatty` | 通知を大量に投げる | 背圧（channel 満杯で読むのをやめる） |

**検出表の解決は `platform::exe::find` を通る**ので、テストでは偽サーバのパスを
検出表の `program` として注入できる口が要る（env か、テスト専用の差し替え関数）。
本番コードへテスト専用の分岐を散らさないこと（`.agent/conventions.md`「テストの書き先は
本番の外」Issue #944 / #1030 / #1022 / #1123）。

一時ディレクトリは**固定名を使わない**（#1666 が既に指摘している型。並行する
`cargo test` 同士で消し合う）。

### (c) 実機（機械検証できない 1 点）

rust-analyzer と実際に握手して `ServerCapabilities` を取得したログの要点を Issue へ貼る。
**偽サーバだけでは「実サーバと握手できる」を示せない**ので、これは省略しない。

## 15. 分割できない理由

「S1 をさらに小さく切れないか」は必ず検討されるので、先に答えを置く。

| 切り方の案 | なぜ成立しないか |
|---|---|
| 「JSON-RPC だけ先に」 | 相手が居ないので**動作を確認する手段が無い**。偽サーバを書いた時点で spawn とライフサイクルが要る |
| 「プロセス管理だけ先に」 | 握手しないプロセスはすぐ終了する。`initialize` まで行かないと「起動できた」が言えない |
| 「位置変換だけ先に」 | これは切れる（純粋関数）。ただし**単独では誰も使わない**ので、切っても PR が 2 本になるだけで価値が増えない |
| 「診断の受信だけ先に」 | `didOpen` が要る = ドキュメント同期が要る = 握手が要る |

つまり **「サーバが起動し、握手し、文書が同期され、位置が変換できる」までが 1 つの動く単位**で、
どこで切っても「動かない半分」が残る。上に乗る #1679 以降は互いに独立なので、
**S1 が入った瞬間から並走できる**（そこで一気に広がる）。

## 16. 判断待ち（着手前にユーザー / master の確定が要るもの）

### 16-1. `lsp-types` の依存追加

新しいライブラリの追加はグローバル規約で「既存の依存で同じことが実現できないかを確認し、
理由を添えて提案する」ことになっている。

| 案 | 内容 | トレードオフ |
|---|---|---|
| **A（推奨）** | `lsp-types 0.97` を workspace deps へ足す | 直近 DL 8,192,033 のデファクト。Zed が同条件（GPUI・tokio なし）で使っている実物がある。追加されるのは型定義中心で tokio を引かない |
| B | 使う型だけ自前定義 | 依存ゼロだが LSP 3.17 の型は膨大。第 2 波の機能追加のたびに手で足すことになる |
| C | `async-lsp`（`default-features = false`） | 多重化・タイムアウトが既製。ただし既定 features に tokio が入り、切れなければ方針違反。`lsp-types 0.95` 固定も持ち込む |

**推奨 = A**（採用実績と方針適合）。C は #1007 の 8 分岐点で既に却下済み。

### 16-2. サーバを起こすきっかけ

| 案 | 内容 | トレードオフ |
|---|---|---|
| **A（推奨）** | **編集モードに入ったとき** | 閲覧しかしないファイルでサーバを起こさない。tako はプレビューで大量のファイルを開く使い方をするので、ここが軽さに直結する |
| B | ファイルを開いたとき | 診断が「開いた瞬間」に出る。ただし閲覧のたびに rust-analyzer が起きる |
| C | 明示 `start` のみ | 最も軽いが、ゼロコンフィグ原則に反する（ユーザーが LSP の存在を知る必要がある） |

**推奨 = A**。§6 の表にはこれを前提で書いてある。

### 16-3. `positionEncodings` に `utf-8` を申告するか

| 案 | 内容 | トレードオフ |
|---|---|---|
| **A（推奨）** | **UTF-16 のみ申告**（Zed と同じ） | 変換層は必須なので、どちらにせよ書く。1 経路だけをテストすればよい |
| B | `["utf-8", "utf-16"]` を申告 | サーバが `utf-8` を選べば変換が恒等になる（わずかに速い）。ただし**サーバごとに経路が変わる** = テストが 2 倍になり、サーバ依存の不具合を呼ぶ。各サーバの `utf-8` 対応は未検証 |

**推奨 = A**。B は S1 が安定してから測って決めればよく、変換層の入口が 1 本なら後から足せる。

### 16-4. サーバ未導入のときに自動導入まで踏み込むか

tako には #1499 / #1509 / #1524 で `setup_deps::offer_and_install`（未検出の依存を [y/N] で
その場導入する 1 実装）が入っている。

| 案 | 内容 | トレードオフ |
|---|---|---|
| **A（推奨・S1 の範囲）** | **案内だけ**（理由 + 次の一手 + 導入コマンド） | S1 の責務に収まる。#1512 で requirements へ入れた「意図して人に残す段」として扱える |

**推奨 = A を S1 でやり、B は #1500 配下の別 Issue として起票する**（S1 の PR を膨らませない）。

## 18. 着地時の差分（#1678 の実装で決めたこと。2026-09-26）

§16 の 4 点は #1678 のコメント（2026-09-24）で確定した: `lsp-types` 0.97 を採用 /
起こすのは編集モードに入ったとき / `positionEncodings` は UTF-16 のみ / 未導入は案内のみ。
実装で上の設計から変えた点と理由:

| 設計 | 実装 | 理由 |
|---|---|---|
| §8 `didChange` は #1651 の `EditDelta` を写す | **サーバへ送った本文の写し**との差分（`tako_core::lsp::sync::diff_change`） | `EditDelta` は `text_edit` の非公開型。同期の合間に編集が溜まる経路（`replace_all`・外部変更・送信キューが満杯で送れなかった回）でも 1 件で正しく当たる。写しは再起動後の `didOpen` と起動中の編集のまとめ送りにも要る |
| §3 `language` + `extensions` + `install_hint_key` | `documents`（拡張子 → `languageId`）+ `install`（OS ごとの導入コマンド）+ `workspace_root` | clangd / typescript-language-server は 1 サーバが複数の `languageId` を持つ。導入コマンドは言語に依存しない文字列で訳が要らず、日英の文は `tako_control::lsp::text` の 1 か所。入れ子の判定も表の値にして「行追加だけ」を保つ |
| §5 印が無ければ `git::repo_root` | `.git` の有無を上へ辿る | `git::repo_root` は `git` を起こす = 編集モードに入った瞬間の UI スレッドで呼べない（#1503 の型） |
| §2 UI スレッドへの bounded 128 のキュー | S1 では置かない。reader が診断を manager の表へ直接書き、送信側を 256 件で頭打ちにする | S1 は UI へ上げる受信が無い（描かない）。表は URI ごとの上書きで開いている文書数が上限。UI へのキューは描画する #1679 が足す |
| §12 MCP の action に `start` | 無し。`restart` が未導入・諦めた・止めたからの起動を兼ねる | 文書の無い `start` はすぐ猶予停止へ入るだけで意味を持たない |
| §11 `status` に stderr の直近 | `logs` だけが返す | 本文を含みうる出力を、求められていない `status` に混ぜない |
| §12 MATRIX の Windows | `Pending`（#1007）+ 根拠 `UnitTest`（偽サーバの e2e が CI の Windows ジョブ） | Windows 実機で実サーバと握手していない（過大申告しない = #591） |

追加したもの: 実行ファイルの差し替え `TAKO_LSP_BIN_<ID>`（ID から機械的に生えるので行追加だけで口も
生える。検証で偽サーバを起こす口でもある）/ 状態「停止中」「止めた」（`stop` の行き先。restart まで
自動では起こさない）/ 同じファイルを 2 つ目のペインで開いたときは断る（LSP は 1 URI に 1 open）。
