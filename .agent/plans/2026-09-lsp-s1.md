## 1. モジュール配置

依存方向は既存どおり `tako-app(ui) → tako-control → tako-core`。**GPUI 依存は tako-app だけ**。

```
tako-core/src/lsp/          新設。プロセスも I/O も持たない純粋部分
  position.rs   UTF-8 バイト <-> UTF-16 コードユニットの相互変換（§4）
  servers.rs    サーバ検出表（§3）。言語追加 = この表への行追加
  root.rs       プロジェクトルート検出（§5）
  state.rs      ライフサイクルの状態機械（純粋な遷移関数。§6）

tako-control/src/lsp/       新設。プロセスと I/O。GPUI 非依存のまま
  rpc.rs        JSON-RPC のフレーミング + id 管理 + タイムアウト（§7）
  server.rs     1 サーバのプロセス管理（spawn / 3 スレッド / shutdown）
  manager.rs    複数サーバの束ね + 開いているドキュメントの登録簿（§8）
  diagnostics.rs 診断の受信と保持のみ（描かない。#1679 が読む）

tako-app/                   S1 では「起動のきっかけ」と status 表示だけ
  preview.rs / main.rs から manager を叩く。LSP の型を UI へ漏らさない
```

`manager` の実体は GUI プロセス（tako-app）が所有する。CLI / MCP は既存どおり IPC を通って
`dispatch` へ入り、`ControlHost` 経由で同じ manager を触る（**CLI と MCP は同じ 1 本を通す** =
`.agent/conventions.md`「CLI と MCP は『同じ 1 本』を通す（Issue #1453 / #1544）」）。

**新しいクレートは作らない。** tako-control は既に GPUI 非依存でプロセスと I/O を持つ層
（`ipc.rs` の accept スレッド・`remote` の daemon）なので、置き場としてそのまま成立する。

## 2. 並行モデル — スレッド + futures channel（tokio も GPUI executor も使わない）

Zed の LSP クライアントは GPUI の `BackgroundExecutor` 上の 3 タスクで動くが、**tako は
それを真似しない**。理由: tako-control を GPUI 非依存に保つ必要があり（依存方向の規約）、
かつ tako には**同じ形の前例が既にある**。

`.agent/architecture.md`「IPC トランスポート」節:

> accept スレッド + 接続毎スレッドのブロッキング IO で受け、リクエストは
> futures channel で UI スレッドへ渡して dispatch する（tokio を持ち込まない方針を維持）

S1 もこれに揃える。**1 サーバにつき 3 スレッド**（Zed の 3 タスクと同じ役割分担）:

| スレッド | 役割 | 詰まったときの振る舞い |
|---|---|---|
| reader | stdout から 1 メッセージずつ読む | 送り先の channel が満杯なら**読むのをやめる**（OS のパイプに背圧を掛け、メモリへ溜めない） |
| writer | 送信キューから取り出して stdin へ書く | サーバが読まなければブロックする（キューの上限で検知） |
| stderr | 1 行ずつ読む | 直近 N 行だけリングバッファに保つ（`tako lsp status` の診断用） |

UI スレッドへの受け渡しは `futures::channel::mpsc`。**bounded** にして上限を
**128 メッセージ**（Zed の `INCOMING_MESSAGE_QUEUE_CAPACITY` の実測値をそのまま初期値にする）。
UI が詰まっているときにメモリを無限に食わないための設計で、tako の #782 / #1001 と同じ問題意識。

大量の通知を受けたときに UI スレッドを飢えさせない配慮（Zed の `yield_now`）は、tako では
「UI スレッド側が 1 フレームで処理する件数に上限を置く」形で持つ（残りは次フレームへ繰り越す）。

## 3. サーバ検出表 — 言語追加は「行追加だけ」

ユーザー要望（#1007 コメント、2026-08-28）:

> ゆくゆくは HTML とかネット系の言語や java とかそこら辺とか，とにかく色々対応させたい

**第 2 波以降の追加コストがこの表の形で決まる。** `tako-core/src/lsp/servers.rs`:

```rust
pub struct ServerSpec {
    /// 安定 ID（設定ファイル・CLI の --name・MATRIX のキーに使う）
    pub id: &'static str,              // "rust-analyzer"
    pub language: &'static str,        // "rust"（LSP の languageId）
    pub extensions: &'static [&'static str],   // ["rs"]
    /// 実行ファイル名。解決は必ず platform::exe::find を通す
    pub program: &'static str,         // "rust-analyzer"
    pub args: &'static [&'static str], // []
    /// ルートの印。上へ辿って最初に見つかったものを rootUri にする
    pub root_markers: &'static [&'static str], // ["Cargo.toml"]
    /// 未導入のときに出す導入コマンド。日英の実文ではなく ui_text のキー
    pub install_hint_key: &'static str,
}

pub const SERVERS: &[ServerSpec] = &[ /* 段階 1 は 4 行 */ ];
```

段階 1 の 4 行（ユーザー確定の順。#1007 コメント）: **Rust（rust-analyzer） → C/C++（clangd）
→ TypeScript / JavaScript（typescript-language-server） → Python（pyright）**。
C/C++ が 2 番目なのは、ユーザー原文の「ヘッダ」が **C/C++ の `#include` ヘッダファイル**と
確定したため。

**表以外に言語名を書かない。** `if language == "rust"` のような分岐を散らすと、第 2 波の
追加が「行追加だけ」で済まなくなる。番犬でこれを止める（§12 の受け入れ条件）。

文言を表に直書きせず `install_hint_key` にするのは #435 / #920 の作法（日英の実文は
`ui_text` 側が持ち、テストに理由文を直書きしない）。tako-core は tako-app の `ui_text` に
依存できないので、**キーだけを表に置き、引くのは tako-app / tako-cli 側**。

## 4. UTF-8 <-> UTF-16 の変換（`tako-core/src/lsp/position.rs`）

LSP 3.17 の既定は **UTF-16 コードユニット**で、UTF-16 対応はサーバ側の必須要件。
`positionEncodings` で `utf-8` を交渉する余地はあるが、**Zed は UTF-16 だけを申告している**
（成熟した参照実装がその最適化を採っていない）ので、**UTF-16 変換層を最初から持つ**。

`TextBuffer` は全てを UTF-8 バイトオフセットで持つ（`text_edit.rs` の不変条件）。
入口を 2 本だけに閉じる:

```rust
/// UTF-8 バイト位置 -> LSP の (0 起点の行, UTF-16 桁)
pub fn lsp_position_of(text: &str, byte_offset: usize) -> (usize, usize);
/// LSP の (0 起点の行, UTF-16 桁) -> UTF-8 バイト位置
pub fn byte_offset_of_lsp_position(text: &str, line: usize, utf16_col: usize) -> usize;
```

既存の `TextBuffer::line_byte_col`（`text_edit.rs`）/ `offset_for_line_byte_col` と**同じ流儀**で
並べる。サロゲートペアが要点（絵文字 U+1F600 は UTF-16 で 2 コードユニット・UTF-8 で 4 バイト）。
`char::len_utf16()` を使う。

**境界の扱いを決めて固定する**: 行の途中で UTF-8 の境界に乗らない位置を渡されたら
**手前の境界へ丸める**（`text_edit.rs` の `snap_boundary` と同じ方針）。サロゲートペアの
片割れを指す UTF-16 桁も同じく手前へ丸める。CRLF の行末は `\r` の手前を行末とする（#1650 で
CRLF 保持が入っているので、`\r` を桁に数えない）。

テストは**日本語 / 絵文字 / タブ / CRLF / 行末 / 空行 / 空ファイル**で両方向を固定する（最低 12 ケース）。

## 5. プロジェクトルート検出（`tako-core/src/lsp/root.rs`）

ファイルのあるディレクトリから上へ辿り、`root_markers` の最初の 1 つが見つかった所。
見つからなければ **`git::repo_root(path)`**（`crates/tako-core/src/git.rs` に既存）、
それも無ければファイルの親ディレクトリ。

Rust の workspace のように印が入れ子になる場合は**最上位**を採る（`Cargo.toml` を見つけても
そこで止めず、上に `[workspace]` を持つ `Cargo.toml` があればそちらを採る）。
これは rust-analyzer の挙動に合わせるための例外で、**表の `root_markers` とは別の判定**に
なるので純粋関数として独立させ、テストで固定する。

**上へ辿る部分は `tako_core::project_root` を使う**（#1656 で Code Runner のプロジェクト既定と
共有する形で新設済み）。境界（HOME の段は見ない / `.git` の段で止まる / 深さ上限 32）は
そこが持つので、LSP 側で辿り方を書き直さない（印がファイル名で表せない探し方は `find_upward_map(start, bounds, probe)`）。git ルートのフォールバックも
`project_root::repo_root_within`（`git::repo_root` は git プロセスを起こすので、
ファイルを開くたびに走る経路には重い）。Rust の workspace の扱いだけは違う:
Code Runner は cargo と同じ「最初に見つかった `[workspace]`」を採るが、ここは
rust-analyzer に合わせて最上位を採る（1 段のワークスペースでは両者は一致する）。

`canonicalize` の結果を持ち回らない（`.agent/conventions.md`「Issue #970」）。
rootUri へ渡す前に `file_uri`（`crates/tako-core/src/file_uri.rs` に既存）で URI 化する。
Windows のドライブ文字・verbatim 表記の扱いは `platform::path::relative_under`（#1569 で新設）と
同じ流儀にする。

## 6. ライフサイクル（`tako-core/src/lsp/state.rs` + `tako-control/src/lsp/server.rs`）

```
[未起動] --(対象言語のファイルを編集モードで開く)--> [起動中]
[起動中] --(実行ファイルが無い)--> [未導入]（理由 + 次の一手を出す。#983）
[起動中] --(spawn 成功)--> [initialize 送信] --(応答)--> [initialized 通知] --> [稼働]
[稼働]   --(プロセス死亡)--> [クラッシュ] --(再起動 3 回まで)--> [起動中] / [諦めた]
[稼働]   --(最後のバッファを閉じた + 猶予 60 秒)--> [shutdown] --(応答 or 5 秒)--> [exit] --> [未起動]
```

遷移そのものは**純粋関数**（`state.rs`）にしてテストで固定し、プロセス操作は `server.rs` が持つ。

| 論点 | 決め | 根拠 |
|---|---|---|
| 実行ファイルの探索 | **`platform::exe::find(name)`（境界 B16）を必ず通す** | #898 / #877 で `which` 直叩きを全部ここへ寄せた。Windows は `PATHEXT` とユーザー導入先まで見る。#1372 で「起動できる形」だけを返すようになっている |
| 起動時の env | `platform::child_cmd`（境界 B21。`command()` / `user_env_cli`） | `.app` を Dock から起動すると PATH が最小構成になる。ログインシェル経由でないと Homebrew のサーバが見つからない |
| コンソール窓 | `platform::process::no_console_window` を通す | Windows で起動のたびに黒窓が明滅しない |
| 未導入のとき | **理由 + 次の一手 + 導入コマンド**（#983 の作法） | 無言で死なない。過去に踏んだ穴 |
| 孤児を残さない | 子の pid を持ち、Drop と GUI 終了経路の両方で kill。生死の判定は **`platform::process::pid_alive`（#1557 / #1581 の境界）** | tako は孤児プロセスで何度も事故っている |
| リクエストのタイムアウト | **120 秒**（Zed の実測値） | `.agent/conventions.md`「外部コマンドを待つときは上限を持つ（Issue #1503）」。無限に待たない |
| shutdown のタイムアウト | **5 秒**（Zed の実測値）。超えたら kill | 同上 |
| 再起動の上限 | **3 回**（指数バックオフ。上限に達したら「諦めた」で止まる） | #813 の「1 回の上限あたり 3 回で打ち切り」と同じ作法。無限再起動でマシンを焼かない |
| 起動のきっかけ | **編集モードに入ったとき**（ファイルを開いただけでは起こさない） | プレビューは閲覧が主で、全てのファイルでサーバを起こすとゼロコンフィグの軽さが壊れる。判断待ち §13-2 |
| アイドル時 | **何も投げない**。タイマーを持たない | #772 の作法。受け入れ条件で実測する |

## 7. JSON-RPC（`tako-control/src/lsp/rpc.rs`）

型は `lsp-types`（crates.io のデファクト。直近 DL 8,192,033）、配線は自作。
既製の JSON-RPC クレートも `async-lsp` も採らない（後者は既定 features に tokio が入る =
tako の「tokio を持ち込まない」方針と衝突する。詳細は §13-1）。

- 送信: `Content-Length: <len>\r\n\r\n<body>`。Zed の実装で 6 行、受信側も 50 行程度
- 受信: ヘッダを `\r\n\r\n` まで読み、`Content-Length` ぶんを `read_exact` して `serde_json`
- **分割受信に耐える**（1 メッセージが複数回の read に割れる / 1 回の read に複数メッセージが乗る）
- id は `enum RequestId { Int(i32), Str(String) }`。応答待ちのハンドラを id で引く
- タイムアウトで待ちを解いたら**ハンドラ表からも消す**（漏れを作らない）
- `$/cancelRequest` を送れる口を S1 で作る（使うのは #1682 の補完）
- サーバからの request（`window/showMessage` / `workspace/configuration` 等）は S1 では
  **既定の応答を返すだけ**。無視して黙らない（サーバが待ち続ける）

## 8. ドキュメント同期と版（`tako-control/src/lsp/manager.rs`）

- `didOpen`: 編集モードに入ったとき。`languageId` は検出表の `language`
- `didChange`: **incremental**。#1651 の `EditDelta`（範囲 + 置換後）を
  `TextDocumentContentChangeEvent { range, text }` へ写す。範囲は §4 の変換で UTF-16 桁へ
- `version`: **#1658 が返すドキュメントの版をそのまま使う**。LSP 用の版を別に作らない
  （2 種類あると必ず食い違う）
- `didClose`: 編集モードを抜けた / ペインを閉じた / ファイルが差し替わった
- 外部変更（#1659 / FR-3.15 のライブリロード）で全文が入れ替わったときは、
  incremental ではなく**全文の `didChange`**（範囲省略）を送る

**サーバが未起動・未導入でも編集経路が壊れないこと**が最優先（ゼロコンフィグ原則）。
同期は「サーバが稼働しているときだけ通る枝」にする。

## 9. 能力ネゴ

`initialize` のクライアント能力は**段階 1 で実際に使うものだけ**申告する
（使わない能力を申告するとサーバが無駄な仕事をする）。S1 では
`textDocument.synchronization`（incremental）と `textDocument.publishDiagnostics` のみ。
機能スライスが自分の能力を足していく。

`positionEncodings` は **UTF-16 のみ**を申告する（§13-3）。

応答の `ServerCapabilities` を保持し、`tako lsp status` で読めるようにする。
**上のスライスは「能力に無い機能を出さない」ためにここを読む**（#1684 の右クリックメニューが
最初の利用者）。

## 10. 診断の受信（`tako-control/src/lsp/diagnostics.rs`）

S1 は `publishDiagnostics` を**受けて保持するだけ**。描画（波線・右パネル）は #1679。
保持はファイル URI ごと。**ドキュメントを閉じたら捨てる**（#830 の「閉じたら解放」の作法）。
件数を数える口を用意し、#1679 の受け入れ条件（閉じたら 0）が測れるようにする。

## 11. ログ（ここだけ規約が厳しい）

AGENTS.md の絶対ルール: ペイン内容・送信テキスト・`TAKO_TOKEN` を診断ログへ出さない。
**LSP の I/O はソースコード本文をそのまま含む**ので、既定で本文を書いてはいけない。

| ログ | 既定 | 内容 |
|---|---|---|
| `perf.log` | ON | method 名・所要時間・結果の種別（成功 / タイムアウト / エラーコード）だけ |
| `persist.log` | ON | サーバの起動 / 終了 / クラッシュ / 再起動の回数。**本文は書かない** |
| `<data_dir>/lsp/<server id>.log` | **OFF** | `TAKO_LSP_DIAG=1` のときだけ。生の JSON-RPC を残す（デバッグ用） |

`tako lsp status` の応答に stderr の直近 N 行を載せるのは**診断として要る**が、
**ソースコード本文が stderr に出るサーバがありうる**ので、行数の上限と
「これは opt-in の診断出力」である旨を明記する。#927 の番犬
（`crates/tako-control/tests/no_personal_data.rs`）の対象はリポジトリのソースなので、
**テストの期待値へ実パスを焼き込まない**こと。

## 12. MCP / CLI の口

S1 で公開するのは**サーバのライフサイクルだけ**（言語機能は各スライスが足す）。

```
tako lsp status  [--name <server id>] [--json]   状態・能力・診断件数・stderr 直近
tako lsp servers                                  検出表と解決結果（導入済み / 未導入）
tako lsp restart [--name <server id>]             止めて起こし直す
```

MCP は **`action` 引数を持つ 1 ツール `tako_lsp_server`**（`status` / `list` / `start` /
`stop` / `restart` / `logs`）。ツールを 3 本増やさない（#513 / #919 と同じ作法。
カタログは 200 KB 以内 = #1540）。#322 の原則どおり、案内するコマンドは常に最簡形
（`tako lsp status`。`--name` は既定で全サーバ）。

T3（`crates/tako-cli/src/main.rs` の `mod platform_matrix_parity`）を通すため
`CLI_KEY_OVERRIDES` へ **`("lsp", "tako_lsp_server")`** を足す。
#1679 以降で言語機能の `tako_lsp` が入ったら、前方一致の最長勝ちを使って
`("lsp status", …)` / `("lsp servers", …)` / `("lsp restart", …)` を `tako_lsp_server` へ、
残りの `("lsp", "tako_lsp")` を言語機能へ振り直す。

`tako-core/src/platform/support.rs` の MATRIX へ 1 マス足す。**Windows で LSP サーバが動くかを
実測しないと `Supported` と言えない**（#591 の規約。過大申告は system prompt 経由で
エージェントを誤らせる）。S1 の段階では実測できたところまでを `windows_evidence` に書く。

## 13. テスト戦略 — 偽サーバ（stdio のモック）

実サーバ（rust-analyzer 等）は CI に入れられない（導入が重い・応答が環境依存）。

### (a) in-process（フレーミングと id 管理）

id の引き当て / タイムアウトでハンドラ表から消えること。

### (b) 実プロセス（spawn・孤児・クラッシュ・再起動）

**テスト専用の偽サーバを Rust で書き、`tako-control` の `[[bin]]`（または `examples/`）として

偽サーバはシナリオを引数 / env で切り替える:

| シナリオ | 振る舞い | 測るもの |
|---|---|---|
| `normal` | 正常に握手して黙る | メッセージ列・アイドル時の無送信 |
| `slow` | initialize に応答しない | タイムアウトが効くこと |
| `crash` | 握手後に自分で落ちる | 再起動の上限 3 回・「諦めた」で止まること |
| `split-header` | `Content-Length` を 2 回に分けて書く | 分割受信 |
| `garbage` | 不正な JSON を混ぜる | 壊れたメッセージで死なないこと |
| `chatty` | 通知を大量に投げる | 背圧（channel 満杯で読むのをやめる） |

**検出表の解決は `platform::exe::find` を通る**ので、テストでは偽サーバのパスを
検出表の `program` として注入できる口が要る（env か、テスト専用の差し替え関数）。
本番コードへテスト専用の分岐を散らさないこと（`.agent/conventions.md`「テストの書き先は
本番の外」Issue #944 / #1030 / #1022 / #1123）。

一時ディレクトリは**固定名を使わない**（#1666 が既に指摘している型。並行する
`cargo test` 同士で消し合う）。

### (c) 実機（機械検証できない 1 点）

## 19. S1 の続き（#1769。2026-09-27）

S1 の着地で「既知の限界」として残した 3 点の決め。

### 19-1. 単独の `\r`

§4 の「行の区切りは `\n` だけ」を改めた。LSP の行は仕様どおり `\n` / `\r\n` / 単独の `\r` で
数え（`position` の入口はすべてこれ）、tako の行（`\n` 区切り）とは `LineIndex::line_byte_col` /
`lsp_position_of_line_col` で行き来する。仕様どおりに数えるだけでは足りなかった
（実測。単独 CR を含む本文を didOpen して定義ジャンプを 2 通りの座標で問う / 未定義の名前の診断の行を見る）:

| サーバ | 問い合わせの位置 | 診断の位置 |
|---|---|---|
| rust-analyzer 1.95.0 | `\n` だけ（仕様の座標に `null`） | 自身の診断は送った本文どおり / flycheck（rustc）は `\n` だけ |
| clangd（Apple 17.0.0） | `\n` だけ（仕様の座標に `[]`） | 仕様どおり |
| pyright | — | 仕様どおり |
| typescript-language-server（TypeScript 5） | — | 仕様どおり |

「サーバごとの数え方」を検出表に持つ案は clangd が 1 つの中で食い違うので成立しない。
**送る本文の単独の `\r` を `\n` に替える**（1 バイト → 1 バイト・UTF-16 の幅も同じ）と、サーバ側に
単独の `\r` が無くなりどの数え方でも同じ行になる（rust-analyzer / clangd とも替えた本文で
仕様の座標に答えることを実測）。写し・`TextBuffer` は替えないので保存はバイト一致。
`didChange` は `\r` の直後から始めない（次の 1 バイトで単独か `\r\n` の片割れかが変わる）。
定義ジャンプの位置の変換は dispatch（画面の 1 行しか持たない）から manager（写しの全文を持つ）へ移した。
限界（どちらも単独 CR を含むファイルだけ）: サーバがディスクから自分で読んだ開いていないファイルは
替えられない（飛び先が単独 CR を含むと rust-analyzer に限って行がずれうる）。rust-analyzer の
flycheck（cargo check = rustc）の診断は rustc がディスクの中身を `\n` だけで数えた行で届く
（実測: 単独 CR の 2 つ後ろの行の型エラーが `line 0, character 45`。rust-analyzer 自身の同じ診断は
`line 2, character 17`）ので、単独 CR より後ろの flycheck の診断は行がずれる。直すには「診断の出所
（`source`）ごとの数え方」を検出表に持つ必要があり、表の形を変える判断になるので #1769 では入れない
（変更前は逆に flycheck だけが合い、rust-analyzer 自身の診断・clangd の診断・pyright・TypeScript が
ずれていた）。テスト: 偽サーバは受けた本文を**自前の模型**で当てて持ち
（`--line-breaks spec|lf`・`--mark`・`echo` の規則・`--doc-log`）、両方の数え方で
`crates/tako-control/tests/issue1769_lsp_followup.rs` が位置の往復とサーバの本文を突き合わせる。

### 19-2. 同じファイルの 2 ペイン目

§18 の「2 つ目は断る」を改め、**1 URI = 1 文書を持ち手で共有**する（エディタで広く使われる形。
master の推奨どおり）。`DocLease` は編集セッション 1 つにつき 1 つで、文書は持ち手の表
（`holders`: 持ち手 → 最後に写しへ取り込んだその持ち手のバッファの版）を持つ。

- `didOpen` は最初の持ち手が開いたとき・`didClose` は最後の持ち手が離れたときだけ
- 版は文書ごとに単調（`max(バッファの版, 前の版 + 1)`。ペインが 1 つならバッファの版そのもの =
  §8「版を 2 種類作らない」は 1 ペインでは変わらない。2 ペインではバッファが 2 つある以上、
  どちらかの版を下回らないよう文書の側で持つしかない）
- **自分のバッファの版が変わった持ち手だけが送る**。版だけで判定すると、変わっていないペインの
  同期（カーソル移動）が相手の編集を巻き戻す往復が起きる
- 加わる持ち手は本文を送らない（相手の未保存の編集を上書きしない）。サーバが見るのは最後に
  編集したペインの本文で、診断はその座標で両ペインへ出る

別案「2 つ目は読み取りだけ」を採らない理由: 2 つ目のペインで打った編集がサーバに届かず、
波線が古い本文のまま残る（どちらのペインで打つかで挙動が変わる = 利用者に説明できない差）。

### 19-3. サーバの解決のキャッシュ

`tako lsp servers` が表の 4 行ぶんログインシェルを起こしていた（起動のたびにも 1 つ）。解決の結果
（見つかった + パス / 見つからない / 打ち切った）を manager が ID ごとに持ち、`servers` と起動が共有する。

- **引き直す合図**: `restart`（名指しならその 1 つ）/ PATH が変わりうる出来事 / 見つかったパスが

  「PATH が変わりうる出来事」= **cwd の変化とコマンドの終わり**を `tako_core::shell_activity` の

### 20-1. 整形の当て方

整形（#1683）は答えを「最初の始まり〜最後の終わり」の 1 か所へまとめて当てていたので、10 万行（8.8 MB）の

つながりの途中が捨てられて undo が半端に戻る ③1 か所ずつ詰め直して本文の長さ × 10 万の転送、になる。

- **決め**: 差分 1 件（`EditDelta`）に離れた箇所の並び（`spans` = 開始位置・置換前後の長さ）を持たせ、置換前 /
  置換後の中身はつないだ 2 本で持つ。整形と補完の確定は同じ `splices_of` → `apply_edit` 1 回（undo 1 回・版 1 つ）
- **書き換えの原始操作 `splice_text`**: 1 箇所はその場で・複数は新しい本文を 1 回で組み直す（行頭索引も 1 回）。
  undo / redo は `EditDelta::splices` で今の本文の座標へ直して同じ口を通す
- **実測**（隔離 GUI・偽サーバの既定の整形 = 10 万行の行末の空白）: 新 = 深さ 2・2,600,298 バイト・undo 1 回で
  整形の前と / もう 1 回で元のファイルとバイト一致。旧（`TAKO_1869_LEGACY=1`）= 深さ 1・17,399,988 バイト・
  その前の打鍵へ戻れない

### 20-2. 補完の読み込み中（真因と直し方）

- **実測**（rust-analyzer 1.95.0・std だけの新しいプロジェクト・250ms おきに `textDocument/completion`）:

  `quiescent:true` の直後にまとめて答える。`didChange` を挟んでも -32801 は 0 件

## 23. 未導入のサーバを取って起こす・エディタの状態表示（#1944。2026-10-09）

§16-4 で「S1 は案内だけ・自動導入は別 Issue」とした、その別 Issue。ユーザーの声は「インテリジェンス機能出てこなくて
不便」で、本番は `pyright not_installed` のまま画面には何も出ていなかった（黙って出ない）。正本は FR-3.41。

### 23-1. 取得元・版の固定・置き場（比べて決めた）

| 論点 | 採った | 比べた案と採らない理由 |
|---|---|---|
| 取得元 | **配布元そのもの**（npm レジストリの tarball / nodejs.org / GitHub Releases）を ureq で取り、tako が展開する | (b) 利用者の `npm install --prefix`: npm が要る（まっさらな環境に無い）・install script が走る・npm の設定（registry / proxy）に依る。(c) brew / winget: グローバルを汚す（Issue の制約）。(d) 自前のミラー: 置き場と署名の運用が要る（tako は配布サーバを持たない） |
| 検証 | **配布元が公開しているハッシュ**をそのまま表に固定（npm = `dist.integrity` の SHA-512 base64、nodejs.org = `SHASUMS256.txt`、GitHub = asset の `digest` の SHA-256）。取得物全体で突き合わせ、合わなければ捨てる | 自分で計算した値を置く案は「どこから来た値か」を説明できない（配布元の値なら照合の経路が公開されている）。署名（npm の provenance / minisign）は配布元ごとに形が違い、検証器が要る |
| 版 | 固定（公開から 2 週間以上置いた版）: pyright 1.1.414（09-09）/ typescript-language-server 5.1.3 + typescript 5.9.3 / rust-analyzer 2026-09-21 / Node.js 24.21.0 LTS | latest を引くと供給網の差し替えをそのまま受ける。ts-ls 6.x は node >= 22.22 を求め、typescript 7.x は OS ごとのネイティブ包みに分かれる |
| 置き場 | `<data_dir>/lsp-servers/<id>/<版>/`（Node.js は `<data_dir>/lsp-servers/node/<版>/node`） | `~/.cache` 等は OS ごとに場所が割れ、`TAKO_DATA_DIR` の隔離（テスト・検証）が効かない。版の段に分けるので版を上げても古い段を上書きしない |
| 展開 | **新しいクレートを足さない**: gzip / deflate は flate2（既存）、tar / zip は `lsp::archive` の自前の読み（ustar + pax の path / zip の中央ディレクトリ → stored / deflate）。パスは `safe_relative` で `..`・絶対パスを拒む | tar / zip クレートは依存の木に無い。読むのは配布元の素直な形だけ |
| 対象 | pyright / typescript-language-server（node が要る）・rust-analyzer（単体バイナリ） | clangd は取らない: macOS の zip が 100 MB（ヘッダ込み）で、C / C++ の解析にはコンパイラのヘッダ（CLT / MSVC）が別に要る。macOS はコンパイラを入れれば `/usr/bin/clangd` も入る |
| Node.js | 利用者の PATH の node が `engines` の下限（pyright 14 / ts-ls 20）以上ならそれ、無ければ Node.js の実行ファイル 1 つだけを取る（macOS は tar.gz の `bin/node`、Windows は zip の `node.exe`） | node を前提にすると「まっさら」で pyright が出ない（Python を書く人は node を持っていないことが多い）。npm・ヘッダは置かない |

### 23-2. 解決の順と状態

**差し替えの env → PATH（`probe_args` があれば動くことを確かめる）→ 置き場（済んだ印を見る）→ 取る**。
グローバルがあればそちらを使う（AC4）。rustup の代理（`~/.cargo/bin/rust-analyzer`）は component が無くても
PATH に居て、起こすと即座に落ちる（諦めた まで 3 回）= 黙って出ない最多の型なので、表の `probe_args`
（`--version`）で確かめて落ちたら `Launch::Broken` = 見つからないのと同じ扱いにする。

状態に「取得中」（`fetching`）を足した。`起動中 --(無いが取れる)--> 取得中 --(取れた)--> 起動中`（同じ起動の
スレッドが続けて spawn する）`/ --(取れない)--> 未導入`。取っているあいだに文書がすべて閉じられたら起こさない
（`FetchedUnused` → 未起動）、stop したら取れても起こさない、restart は世代を進めて新しい起動の流れが錠を待って
結果を受ける。未導入から使えるようになったら（取れた・install・引き直しで見つかった）`Installed` で起こす。

### 23-3. 失敗と取り直し

失敗の型は `network` / `http` / `digest` / `too_large`（配布元の大きさの 2 倍 + 1 MB を超えたら打ち切る）/
`io`（ディスクの空き・権限）/ `archive` / `unsupported`。どれも理由を記録して未導入へ落ち、**今の案内（導入コマンド）を
残す**。失敗の記録があるあいだは開き直しても自動では取り直さない（オフラインで開くたびに 15 秒の接続待ちをしない）。
取り直しは `tako lsp install` / `restart` / 画面の「もう一度取得」。途中の段（`.partial-*`）は失敗で消し、落ちた
プロセスの跡は 1 時間より古いものを次の取得が掃除する。

### 23-4. 導入を検知したら起こす（#1823 の 2）

`tako_core::shell_activity::subscribe` で合図（cwd の変化・コマンドの終わり）を受け、未導入の記録があれば背景の
スレッド 1 本で引き直す（キャッシュは合図の番号で古くなっている）。ログインシェルをコマンドごとに起こさないよう
**間隔 15 秒**（`RECHECK_INTERVAL`。#1977 で直前の 1 巡にかかった時間 × 50 を 15 秒〜5 分に収める形へ = §24-3）をあけ、間隔の中に来た合図は明けたときに 1 回だけ引き直す。外の端末で入れた
ときは合図が来ないので restart が要る（未導入の次の一手の文がそう言う）。

### 23-5. 画面

タイトル（ファイル名の並び）に 1 行: 「<サーバ> を取得中（<取得物> n / m MB）」「起動中」「読み込み中」「動作中」。
未導入・取得の失敗・諦めた・止めたはタイトルの下の帯（外部変更の競合の帯と同じ置き方）に見出し（補完・診断が
出ないこと）+ 理由 + 次の一手 + ボタン（入れる / もう一度取得 / 起こし直す）。帯は「出ない」状態のときだけなので、
動いているときの本文の高さは変わらない。タイトルが狭いときは **ファイル名 > 状態 > パス** の順で残す（状態が出ている
ときだけファイル名を縮めず、パスを重み 50 で先に縮める。初版はファイル名が「main…」まで潰れた = 採取で見つけた退行）。

#1977 で最初の診断まで待って問い直す = §24-1。visual-test は読み込みが済んでから打ち、出なければもう 1 文字打つのを保険に残す）。状態の口 `LspManager::document_server` は待たない（ロックと印の stat）。
描き直しのきっかけは manager の状態の知らせ（`LspManager::state_events`。**診断の知らせとは別の口**で、容量 1 の起こすだけの口 + 「つながりを作り直す」フラグ。取得の進捗は描き直すだけで 200ms おき。初版は診断の口に空の URI を混ぜて #1679 の「運ぶのは URI だけ」を崩し、e2e `ui_へのキューは上限で頭打ちになり溢れた印が立つ` が落ちた）。

### 24-2. 古い版の置き場の片付け

`fetch::sweep_old_versions`（判定は `tako_core::lsp::fetch::sweep_plan`）。呼ぶのは今の版の段が済んだとき（取れた・
置き場から起こした・`tako lsp install`）で、背景のスレッド（起動の流れ・install の offload）から。消すのは
**tako の印（`.tako-installed`）がある・今の版より前に入った・生きている tako が使っていない**段だけ。

- 「前に入った」は印の `installed_at`（壊れていれば印の mtime）で比べる。今の版より後に入った段（新しい tako が入れた）を
  残すので、同じ data dir を古い tako と新しい tako が共有しても消し合って取り直し続けない
- 置き場から起こす tako は版の段に `.tako-lease-<pid>` を置く（起こす直前）。pid が生きている段は消さない
  （古い GUI が古い版の pyright で動いている = typeshed を遅れて読むので、消すとその GUI の補完が壊れる）。
  終わった pid の印は片付けのついでに外す
- 先に名前を外す（`.partial-old-<版>-…` へ rename）してから消す。Windows で使用中の実行ファイルがあれば rename が断る =
  半端に消えた版を残さない。消し損ねた跡は次の片付けと取得の掃除が拾う
- 結果は `tako lsp status` の `fetch.cleanup`（removed / kept / freed_bytes / secs_ago）と `tako lsp install` の各行の
  `cleanup`。表から消えたサーバの段は見ない（その ID の表の行が無い = 今の版と比べられない）

### 24-3. 引き直しのコスト

引き直しはサーバ 1 つにつきログインシェル 1 本（`$SHELL -l -c 'command -v …'`）。実測（macOS・zsh・5 回）: 普通の rc

重い rc で CPU 1 コアの約 10%。そこで間隔を `recheck_interval` = 直前の 1 巡にかかった時間 × 50 を 15 秒〜5 分に
収める形にした（普通の rc は 15 秒のまま・重い rc は約 100 秒。どちらも引き直しの占める時間は 2% 前後）。様子は
`tako lsp status` の `recheck`。合図は UI スレッドの OSC の処理（`TerminalSession::process_osc_event` → `shell_activity::note`）

## 26. tako の外で変わったファイルの通知（#2034。2026-10-14）

#1685 の実測で、`cargo fmt` を当てた後も rust-analyzer が整形前の行番号で参照を返した。真因は tako が
`workspace.didChangeWatchedFiles` を申告せず、サーバの `client/registerCapability` を null で答えて捨てていたこと。
申告が無いと、開いていないファイルの外での変化を拾えるかは**サーバ自前の監視次第**になる。rust-analyzer 1.95 は
自前の監視（FSEvents）へ落ちるが、**根がシンボリックリンクを通ると拾わない**（実測。stdio のハーネスで外で 3 行
足した後の `lib.rs` の参照: 申告なし・根が `/var/folders/…` = 0 行目のまま / 申告なし・根が実パス = 3 行目 /
申告して知らせる・根が `/var/folders/…` = 3 行目。FSEvents が実パスで知らせ、rust-analyzer の監視が渡された
綴りの根と照合できないため）。申告すると `**/*.rs` / `**/Cargo.{lock,toml}` / `**/rust-analyzer.toml` を根ごとの
相対パターンで、利用者の設定ファイルと `Cargo.toml` を絶対パスで登録してくる。

tako の GUI から開いた文書は `OpenFile` が実パスへ直す（`dispatch` の `canonicalize`）ので、rust-analyzer へ
渡る根はふだん実パスで、自前の監視が効いていた（隔離 GUI の旧腕で `cargo fmt` の後も整形後の行 = 実測）。
**#1685 の実測で見えたずれがどの経路だったか（リンクを通る根か、自前の監視が効かない別の条件か）は特定していない**。
tako が見て知らせる形にすれば、根の綴りにもサーバの自前の監視の有無にも依らずに効く。

### 26-1. 置き場と流れ

| 層 | 持つもの |
|---|---|
| `tako_core::lsp::watch` | 登録の読み取り（id ごと・`unregisterations` の綴りも）・グロブの照合（`globset`）・監視する根・根の整理（重複と配下を畳む・広すぎる根を外す）・種別の決め方 |
| `tako_control::lsp::watch` | `WatchHub`（`notify` の監視 1 つ + まとめ送りのスレッド 1 本）・実パスを渡した綴りへ戻す |
| `tako_control::lsp::server` | reader がサーバの要求を `Handlers::on_request` で見せてから既定の応答を返す |
| `tako_control::lsp::manager` | 登録を `Slot::watch` へ・根を揃える（`refresh_watch`）・まとめた変化を当たるサーバへ送る（`on_watched_files`） |

ロックの順は `watch` → `inner`（`inner` を持ったまま監視を触らない）。登録はプロセスのものなので、`begin_spawn` /
`on_exit` / `shutdown_all` で捨て、`on_exit` の後に根を揃え直す（どのサーバも登録していなければ監視ごと落とす）。

### 26-2. 比べて決めたこと

| 論点 | 決め | 理由 |
|---|---|---|
| 監視の手段 | `notify` 8.2（既存の依存。表示中プレビューの #233 と同じ） | FSEvents / ReadDirectoryChangesW のイベントだけで走査しない（#2011 と衝突しない）。新しいクレートは増えない |
| グロブ | `globset` 0.4（`ignore` 経由でツリーに既にある版） | LSP のグロブ（`**` / `{a,b}` / `[!x]`・`*` は区切りを越えない）をそのまま読める。`regex` へ自前で訳す案は採らない |
| 監視の数 | manager 全体で 1 つ（全サーバの根の和） | スレッドがサーバの本数に比例しない（監視 1 本 + まとめ送り 1 本） |
| 文字列のグロブ（base 無し） | `/` か `C:/` で始まれば絶対パス、それ以外はそのサーバの根からの相対 | 根の外のファイルを別のサーバの根を見ている監視から拾わない |
| 種別 | 最後に在るか + 窓の中で作成を見たか | OS の種別は rename・削除 + 作成で取り違える。サーバは作成と変更をどちらも読み直す |
| 広すぎる根 | HOME とその祖先・FS の根は監視しない（`skipped` に `broad`） | FSEvents は非再帰でも配下全体のイベントを届ける = 非再帰にしても費用が減らない |
| 開いている文書 | 知らせは送る（サーバが捨てる）。本文は #1659 の読み直し → `didChange` | VS Code / Zed と同じ。LSP の約束で開いている文書の中身はクライアントのもの |
| 溢れ | 走査で取り戻さない（`overflows` を数える） | 走査しない約束を守る。Windows のバッファ溢れのときだけ起きうる |

## 28. 隔離起動では自動で起こさず・取らない（#2048。2026-10-16）

#1691 の検証で、隔離 GUI（`TAKO_ISOLATED=1`）で編集を始めるとタイトルに「rust-analyzer 起動…」が出た。
rust-analyzer は初回にワークスペース全体の `cargo check` を走らせ（#2035）、#1944 の取得経路に入るとネットワークへ出る
= 他の検証の CPU / メモリと結果を汚す。正本は FR-3.28（起こすほう）と FR-3.41（取るほう）。

### 28-1. 決めたこと

| 論点 | 採った | 比べた案と採らない理由 |
|---|---|---|
| 止める範囲 | **自動起動と自動取得の両方**（master の判断。隔離の検証を汚さないのが目的） | 取得だけ止める: rust-analyzer が PATH にある機では `cargo check` が走ったまま |

## 29. 初期化オプションの既定と rust-analyzer の target の分離（#2035。2026-10-16）

#1685 の実測で、tako が rust-analyzer に初期化オプション（`initializationOptions`）を渡していないため、起きた直後の
build script と proc-macro を作る段と、読み込みが済んだ直後の最初の flycheck（`cargo check --workspace --all-targets`）が
**利用者と同じ `target/debug`** で走っていた。cargo は target のロックを 1 本の cargo にしか持たせないので、そのあいだ
（tako 自身で約 5 分）利用者の `cargo build` は待たされる（cargo 1.95 の表示は
`Blocking waiting for file lock on artifact directory`）。正本は FR-3.28。

### 29-1. 比べた案

先に確かめた事実（cargo 1.95 の実測）: **同じ target でも check と build の成果物は別のファイル**になる
（`cfg-if` を build → check すると `libcfg_if-<別のハッシュ>.rmeta` が増える）。つまり「分けないならディスクを
食わない」ではなく、分けなくても check の成果物は `target/debug` に増える。分けて 2 重になるのは
**build script と proc-macro（とそれらが依存するホスト向けの成果物）だけ**。

| 案 | ディスク | 初回の所要 | ロックの待ち | 採否 |
|---|---|---|---|---|
| A. 分けない（変更前 = 何も送らない） | 増えるのは check の成果物だけ（tako 自身で約 2.2 GB = §29-3 の内訳）。build script・proc-macro は利用者の build と共有 | 利用者が先に build していれば build script・proc-macro を作り直さないぶん B より短い（#1685 の実測で tako 自身約 5 分） | **初回の check のあいだ利用者の `cargo build` が待つ**（実測: 注入で 20 秒眠る build script の最中に撃った `cargo build` が 20 秒待った）。保存のたびの check でも同じ | 採らない |
| **B. 分ける（`cargo.targetDir = true`）** | A に加え、build script と proc-macro（とそのホスト向けの依存）が `target/rust-analyzer` にもう 1 組（実測 tako: 2.93 GB のうち 2 重になるのは build script 0.14 GB + proc-macro 0.09 GB + ホスト向けの rlib 0.48 GB = 約 0.71 GB。利用者の `target/debug` 20.8 GB の約 3%） | build script・proc-macro も作るぶん A より長い（実測 tako: 開いてから 232 秒・`CARGO_BUILD_JOBS=4`） | **待たない**（実測: 同じ手順で 1 秒・Blocking 0 行。tako 自身でも check の最中に撃った `cargo build -p tako-core` が 5 秒・Blocking 0 行） | **採る** |
| C. 場所を指定して分ける（`cargo.targetDir = "<path>"`） | B と同じ | B と同じ | 待たない | 既定にはしない（プロジェクトの外へ置く理由が無く、`cargo clean` で一緒に消えなくなる）。上書きで選べる |
| D. 初回の check を後回し・切る（`checkOnSave = false`） | A と同じ | 起動直後の flycheck が無くなる | build script・proc-macro の段は残る = 待ちは残る。保存の check も止まり、借用検査などの rustc の診断が出ない | 採らない（rust-analyzer に「初回だけ遅らせる」設定は無い） |
| E. 優先度を下げる（`nice` / `taskpolicy -b` / `-j` を絞る） | A と同じ | 延びる | **ロックを握る時間が延びる = 待ちは長くなる** | 採らない（ロックは解けない。CPU の取り合いは #1992 の `tako queue` の領分） |
| F. build script / proc-macro を切る（`cargo.buildScripts.enable` / `procMacro.enable` = false） | 小さい | build script の段が無い | flycheck の段の待ちは残る | 採らない（derive・`OUT_DIR` の生成コードが解けず嘘の診断が出る） |

### 29-2. 決めたこと

- **既定 = rust-analyzer へ `{"cargo": {"targetDir": true}}`**。ロックの待ちを消せるのは B / C だけで、費用（ホスト向けの
  成果物の 2 組目）は rust-analyzer の設定の説明そのもの（"This prevents rust-analyzer's cargo check and initial build-script
  and proc-macro building from locking the `Cargo.lock` at the expense of duplicating build artifacts."）。置き場は
  `<target>/rust-analyzer` = 既存の target の下なので `.gitignore` の `target/` に入り、`cargo clean` で一緒に消える。
  `CARGO_TARGET_DIR` を使っている人はその下に作られる（rust-analyzer の規則）
- **置き場は検出表の列 `init_options`**（キー = ドット区切りの経路・値 = JSON の字句）。言語の追加 = 行追加だけを保つ。
  既定を持たない行は何も送らない = 変更前と同じ initialize（e2e で pyright の行を確かめる）。重ね方（既定 + 上書き →
  入れ子のオブジェクト）は `tako_core::lsp::init_options` の 1 実装
- **上書きは settings.json の `lsp_init_options`**（サーバ ID → キー → 値。利用者が変えたキーだけを持つ）。env は Dock から
  起こした GUI へ渡せず、rust-analyzer 自身の `rust-analyzer.toml` は tako から実効値を読めないので口にしない（置けば
  rust-analyzer がそれも読む。どちらが勝つかは rust-analyzer の規則で、tako は未実測）。書く口は `tako lsp options --name <ID>
  --set KEY=VALUE`（値は JSON か文字列・`null` で既定へ戻す）と MCP `tako_lsp_server` の action=options（`set`）の 1:1 で、
  中身は `dispatch::lsp_server_action` の 1 実装。tako が起動していなくても CLI のプロセスで同じ実装が読み書きする
  （#1944 の install と同じ）。新しい MCP ツールは足さず、action と `set` だけ（カタログ +241 B）
- **効くのは次に起こしたときから**。動いているサーバへは送り直さない（tako は設定の変更を知らせる口
  `workspace/didChangeConfiguration` を使っていない。今すぐ効かせるなら `tako lsp restart`）。本番の manager は
  **起こすたびに settings.json を読む**ので、手で直した settings.json も次の起動から効く
- **読む口**: 実際に送った値は `tako lsp status` の各サーバの `init_options`、既定・上書き・実効値と「動いているサーバへ
  送った値がいまの実効値と同じか」は `tako lsp options` の `servers[].options` / `effective` / `running[].sent` / `current`
- A/B は `TAKO_2035_LEGACY=1`（何も送らない）
- 他の言語サーバに同種の既定が要るか: 表の行のうち、利用者のビルドと同じ出力先を取り合う初回の処理を持つのは
  rust-analyzer だけと見ている（clangd の索引は `.cache/clangd`、sourcekit-lsp の背景の索引は `.build/index-build` に
  自前で分けている。どちらも資料による判断で未実測）。実測して要ると分かった行は、この列へ 1 行足すだけで載る

### 29-3. 実測

実の rust-analyzer 1.95.0・cargo 1.95.0・隔離 GUI（`scripts/test-lsp-target-dir-2035.sh`。2026-10-16）。

| 測ったもの | 新（既定 = 分ける） | 旧（`TAKO_2035_LEGACY=1`） |
|---|---|---|
| rust-analyzer の初回の build script が走った場所（注入の build.rs が記録した `OUT_DIR`） | `target/rust-analyzer/debug/build/…` | `target/debug/build/…` |

## 30. 全文を 1 つの書き換えで返す整形を行ごとへ割る（#1899 の 1 点目。2026-10-25）

### 30-1. 何が残っていたか

#1869 で整形は「離れた箇所ごとの差分を 1 件に並べる」形になったが、行単位の差分を返さず**文書全体を 1 つの
`TextEdit` で返すサーバ**の答えは、`order_changes` の最小化（同じ頭と尻を削る）をしても最初に変わった所から
最後に変わった所までの 1 か所が残る。10 万行の行末の空白を消す答えなら本文 2 本ぶんを undo へ積み、予算 8 MiB を
超えてその前の打鍵の履歴を捨てていた（#1869 前の 1 範囲と同じ症状）。

### 30-2. 決め

- **割るのは当てる段だけ**（`TextBuffer::apply_changes` の中、`order_changes` の後）。範囲の整形の
  `restrict_to_range` は割る前の答えで判定する = 範囲の整形の結果は変わらない。補完の確定（`replace_position_ranges`）は割らない
- **突き合わせ** = `tako_core::text_diff::changed_regions`（表示用の `diff_lines` は変えない）: 共通の先頭・末尾を削る →
  両側に 1 回ずつ現れる行を目印に区間を割る（patience。目印探しの総量は行数の 8 倍で頭打ち）→ 目印の無い区間だけ
  Myers（上限 1,000 を超えた区間は丸ごと 1 区間）。鍵は**行の前後の空白を除いた中身**
- **置き換えの組み方**（`text_edit::line_split`）: 中身の同じ行は頭の空白と尻の空白（改行を含む）を別々に、中身の
  違う区間は頭から 1 行ずつ対にして余りを 1 か所で消す / 足す。どれも置換後の本文を順に並べた形なので、当てた本文は
  割らないときとバイト一致
- **重さの決め**: 1 か所ごとに表（`DeltaSpan` 24 バイト）が増えるので、隣とのあいだ（変わらない本文）が 12 バイト
  未満ならまとめる（まとめると履歴が 2 × あいだ 増えて表が 1 つ減る。あいだごとに独立なので前からの貪欲で最小）。
  それでも割らないほうが軽ければ割らない。最初は「1 MiB までは重くなっても割る（カーソルのため）」にしていたが、
  実の rust-analyzer（もともと細かい差分を返す）で undo の履歴が 11% 増えたのでやめた
- 割るとカーソル・選択端も同じ行の同じ中身に留まる（割らないと書き換えの頭からの距離を保つだけ）。応答の
  `changes`（CLI / MCP）は割った後の箇所の数
- GUI の再ハイライトの範囲（`preview.rs` の `changed_lines`）は本文の前後の比較で決まるので割り方には依らない
- 偽サーバの規則 `whole: true`: 既定の整形（行末の空白を消す）を当てた全文を 1 つの `TextEdit` で返す。
  A/B は `TAKO_1899_LEGACY=1`（割らない）
