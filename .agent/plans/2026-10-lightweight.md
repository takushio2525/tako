# 描画と RAM の徹底的な軽量化の計測と計画（Issue #2011 S0）

> エピック #2011 の S0。**製品コードは 1 行も変えていない**（足したのは計測スクリプト
> `scripts/measure-footprint-2011.sh` 1 本）。土台は main（`66813d7`）。
> 数値はこの PC（Apple M5 Max・36 GB・macOS 26.4）で 2026-10-13 に測った。本番 GUI（v0.8.31）は
> **読み取りだけ**（`footprint`・`proc_pid_rusage`・`ps` / `pgrep`・corpse へ打つ `heap`・CLI の状態読み）、
> 構成を変える計測は隔離 GUI（シンボル付き release・tako-vd・窓 1600×1000 pt 固定）で行った。
> 子 Issue の一覧と依存は §6（正本は #2011 のコメント）。#2009（S1）との境界は §4。

## 0. 結論（先に要点）

- **本番 835 MB（再起動前）の中身は「プレビュー」と「描画」でほぼ半々**（§2.1）: malloc 408 MB のうちプレビューのキャッシュ 173 MB、
  描画の実質 408 MB のうちプレビューを載せた GPU のアトラス 約 150 MB・窓の drawable 3 面 61 MB・**窓にもペイン数にも依らない固定 約 150 MB**。
  ターミナルのグリッドは器 26 枚で見積もり 1.6 MB しかない（器は代替画面・履歴 0 で、履歴は tmux 側。**二重には持っていない**）。
  #814（2026-08）の後は 129 MB だったので、2 か月で 3〜6 倍に戻っている
- **CPU の最大は描画でもメモリでもなく「監視スキャン」**（§2.2）: tako-app の回収済みの子プロセスが 1 コアの **24.4%**（本体 18.7% より大きい）。
  中身は master の監視が 4 秒ごとに `zsh -l -c '…; claude agents --json'` をアカウント 4 つぶん起こしている 60 本/分だけで、
  4 秒ごとに約 600 MB の一時的な山も作る。#1880 で状態の一次ソースは mod の報告になっているのに、走査は止まっていない
- **本体の CPU のほとんどは描画**（§3.4）: 出力中の 1 枚で 7.4%、うち画面ロック中（描かない）でも残る取り込みは 1.6 ポイント。
  描画 1 回あたり約 0.2〜0.25 ポイントで、本番の「描画 66 回/秒・本体 18.7%」と同じ比率。アイドル時も GPUI の display link が
  毎 vsync 起きる（0.5〜0.9%・wakeup 約 95 回/秒）
- **1 枚あたりの持ち分**（§3.3）: 直接・裏 15.4 MB（3000 行。履歴を行ごとに列幅ぶん持つ）/ 器・裏 5.1 MB（tako 側は 0.4 MB、残りは tmux）/
  器・退避 3.8 MB / プレビュー 5 枚で malloc +112 MB。**本番は器が既定なので、ペイン数より「プレビュー」と「描画の固定分」が効く**
- **#2009（S1）と重なるもの**（プレビュー・動画・描画メモリの内訳・器の裏のペイン）は子 Issue にせず §4 の実測を渡した。
  重ならない側で 7 本を起こした（§6）: 監視スキャン（S2 #2017・CPU −20 ポイント以上）/ ペインログの取り込み（S3 #2018）/
  malloc の保持を返す（S4 #2019・約 50 MB〜）/ `sessions.yaml` の 30 秒ごとの全体書き直し（S5 #2020・約 2.3 GB/日）/
  MCP ブリッジ（S6 #2021・26 本で約 80 MB）/ アイドルの display link（S7 #2022・提案）/ 回帰の番犬（S8 #2023）
- **回帰を止める計測**: `scripts/measure-footprint-2011.sh`（§7）が同じ条件で footprint・アイドル CPU・描画回数・起動時間・スレッド・電力を出す。
  描画の値は「描いている最中」かつ「蓋が開いて画面がロックされていない」時しか取れない（§1.3・§3.2）ので、その欄を行ごとに記録する

## 1. 計測の方法

### 1.1 本番（読み取りだけ）

| 何を | どう測ったか |
|---|---|
| メモリ | `footprint -p <pid>`（区分つき）/ `footprint -j`（JSON）。RSS は使わない（描画面と圧縮分が載らず、835 MB の時に RSS は 162 MB だった） |
| ヒープの中身 | `heap --forkCorpse -s -H --showSizes <pid>`（**corpse へ打つので本体は止めない**。MallocStackLogging が無いので出どころは出ない） |
| CPU・電力 | `proc_pid_rusage(pid, 6)` の差分（user / system・**回収済みの子**の user / system・`ri_energy_nj`・wakeup。`ps -o time` に子の分は出ない。powermetrics は sudo が要るので使えない） |
| 子プロセス | `pgrep -lf -P <pid>` を 10 Hz で 60 秒（短命な子は一意な pid で数える） |
| 描画回数 | `tako redraw-limit` の `body_renders`（ペイン本体を実際に描いた回数）と `flushes`（出力起因の再描画の要求）を 2 回読んだ差 |
| ディスク | `du -sk`・`stat -f %m`（書き直しの頻度は 1 秒ごとの mtime） |

### 1.2 隔離 GUI（`scripts/measure-footprint-2011.sh`）

§7 に使い方。同じ release バイナリ・同じ窓の寸法・同じ中身（3000 行・日本語を含む）で、
「① 放置 60 秒」と「② 表に 1 枚足して 1 行 10ms で出し続ける 60 秒」の 2 区間を測る。
ヒープの出どころだけは別に、`MallocStackLogging=lite` を付けた隔離 GUI に std 構成を組み、
`malloc_history -allBySize -fullStacks` を「最初の持ち主フレーム」別に集計した（§3.1）。

### 1.3 footprint の数え方の罠（**`swapped` を足さない**・**描いている最中に測る**）

`footprint -j` の区分ごとの `dirty` は**圧縮・スワップされた分を既に含み**、`dirty` の和が `phys_footprint` と一致する
（本番で 195.4 / 195.5 MB）。`swapped` を足すと二重に数え、メモリ圧が高い時に malloc が合計を超えた（S0 の途中で踏み、
最初は「描画の区分が重なっている」と誤って読んだ）。スクリプトは `dirty` だけを足し、描画は
「合計 − malloc − 描画以外の区分」で出す（`gfx_mb`）。テキストの `footprint -p` の Dirty 列は最初から正しい。

**描画資源は描いている最中しか計上されない**。隔離 GUI を放置すると 40 秒前後で `phys_footprint` そのものが
270 → 92 MB へ落ち、描き始めると戻る（#1968 が本番で見た「370 ↔ 550 MB の往復」と同じ現象）。
本番はエージェントが出力し続けるので**ほぼ常に描いている側**にいる。比べるときは「出力中」の値を使う。
**蓋閉じ・画面ロック中はフレーム自体が組まれない**ので、その間の描画の値は未実測（§3.2）。

### 1.4 計測の条件

- **蓋**: 開いた状態で測った（`AppleClamshellState = No`）。どの行も出力中に本体の描画が
  29〜30 回/秒起きている（= フレームが組まれている）ことを確かめた。蓋を閉じた機ではフレームが組まれない
  ことがあり（memory: lid-closed-no-frames）、スクリプトの `drawn` 欄が「なし」になる
- **PC の再起動**: 11:01 に別プロジェクトの Playwright WebKit の GPU プロセスが footprint 55 GB まで膨らみ
  （swap 12 GB 中 11.2 GB・圧 4）PC が再起動した。本番の数値は**再起動前（v0.8.31・起動 80 分）**と
  **再起動後（起動 17〜40 分）**の 2 回で、どちらかを明記する。隔離 GUI の計測は再起動後に load が
  10 未満・メモリ圧 1 へ落ち着いてから行った
- メモリ圧の暫定ルール（圧 4 なら 2 以下まで待つ・`CARGO_BUILD_JOBS=2`）に従った

- #814（2026-08）の後は本番 **129 MB**（9 タブ・プレビュー 6）だった。2 か月で 3〜6 倍に戻っている
- **器のペインのグリッドは小さい**: 本番の器 26 枚はすべて代替画面（`alt_screen: true`）・履歴 0 行で、
  `(履歴 + 行) × 列 × 24 B` の見積もりは全部で **1.6 MB**。器の履歴は tmux 側にしか無い（tako 側で二重に持っていない）
- **生きている割り付けと malloc の差**: corpse の `heap` で生きている割り付けは 128,203 個・144.5 MB。
  うち 2 MiB × 27 個（54 MB）はペインごとの PTY 読み取りバッファ（`pty_loop.rs`）で、同じ確保を隔離 GUI の
  `vmmap` で見ると 1 本あたり **16 KiB しか触れていない**（確保の大きさ ≠ 常駐）。残りの生きている割り付け約 90 MB に対し malloc の区分は
  136〜139 MB で、**差の約 50 MB は解放済みなのにアロケータが手元に持っているページ**（ピークは 460 MB なので、大きな一時的な割り付けの後はもっと開く）

### 2.2 CPU（本体 / 子）と子の中身

`proc_pid_rusage` の差分（再起動前・60 秒）:

| 指標 | 値 |
|---|---|
| tako-app 本体（user + system） | 11.2 秒 / 60 秒 = **18.7%**（1 コア比） |
| 回収済みの子プロセス | 14.7 秒 / 60 秒 = **24.4%** |
| 電力（本体の `ri_energy_nj`） | 18.7 J / 60 秒 = 0.31 W（子の分は含まない。CPU 比で按分すると子は約 0.4 W = 推定） |
| 割り込みの wakeup | 418 回/秒 |
| 起動からの累計（80 分） | 本体 342 秒 / 子 1,469 秒（子が本体の 4.3 倍。#1968 の「4〜6 倍」と同じ傾向） |
| 描画回数（20 秒の差） | ペイン本体の描画 **66.2 回/秒**・出力起因の要求 28.8 回/秒（表の 8 枚のうち数枚でエージェントが出力中） |

**子の中身はほぼ 1 種類だけ**: `pgrep -lf -P <pid>` を 10 Hz × 60 秒で拾うと、短命な子は
`/bin/zsh -l -c '[export|unset] CLAUDE_CONFIG_DIR…; claude agents --json'` だけだった。一意な pid は
**60 本/分 = 走査先 4（登録アカウント 4）× 15 回/分**。

```sh
# 1 本のコスト（/usr/bin/time -l・3 回とも同じ値）
zsh -l -c true                              # real 0.15 s・user 0.05・sys 0.06・maxrss 7 MB
zsh -l -c '…; claude agents --json'         # real 0.32 s・user 0.13・sys 0.06・maxrss 148 MB
claude agents --json（実体を直接）            # real 0.15 s・user 0.12・sys 0.06・maxrss 148 MB
```

- 走査は `worker_status` / `orchestrator self` の**監視**（鮮度 5 秒・`AgentScanFreshness::Monitoring`）が起こしている。
  #1011 で UI 用は 30 秒に分けたが、監視側は 5 秒のまま。#1968 も「最大の子プロセスの CPU はこの走査で、本 PR の対象外」と記録して残していた
- `worker_status` は会話 ID が取れると `query_agent_status`（= 走査）を**無条件に**呼ぶ
  （`crates/tako-control/src/dispatch.rs` の `let agent = orchestrator::query_agent_status(sid);`）。
  #1880 で状態・ctx・権限待ちの一次ソースは mod の報告になり、mod の報告は会話 ID・モデルも運んでいる
  （`claude-mod/hooks/register.ts` の `session_id` / `model`）のに、走査は止まっていない
- 走査 1 回は 4 本を並行に起こすので、**4 秒ごとに約 4 × 148 MB = 約 600 MB の一時的な山**ができる（PC 全体のメモリ圧 = #1992 にも効く）
- キャッシュは鮮度 5 秒の 1 本を mutex で直列化しているので、コード上は 12 回/分が上限のはず。**実測は 15 回/分**で、差の出どころは未確定

## 3. 隔離 GUI の実測

### 3.1 ヒープの出どころ（論点 1）

`MallocStackLogging=lite` を付けた隔離 GUI（器・表 4・裏のタブ 8・退避 18・プレビュー 5）を組み、
40 秒後に `malloc_history <pid> -allBySize -fullStacks -q`（14 MB・24,133 束・3 秒）を採って、
各束を「malloc の内部と Rust の割り付けの内部（`alloc::` / `core::` / `std::` / `hashbrown::` …）を飛ばした
最初のフレーム」へ帰属させた。**1 回 256 KiB 以上の割り付けは確保の大きさと常駐が一致しない**
（PTY の読み取りバッファは 2 MiB 確保して 16 KiB しか触れていない）ので分けて、常駐は `vmmap -v` の
dirty + swap で見た。

| 持ち主（1 回 256 KiB 未満 = 確保 ≒ 常駐） | MB |
|---|---|
| `tako_app::preview::SyntectHighlighter::step`（コードのプレビューの構文の塗り） | 10.42 |
| `alacritty_terminal::grid::resize`（30 枚のグリッド。器なので 1 画面ぶんだけ） | 7.41 |
| `tako_app::preview::load_pdf_with_key` | 5.60 |
| PTY のループのスレッドの立ち上がり（30 本 × 80 KiB の calloc 等） | 3.75 |
| `gpui::text_system::WindowTextSystem::shape_text` | 0.88 |
| ObjC / CoreFoundation / CoreGraphics / CoreText（合計） | 約 7 |
| **クレート別**: tako_app 16.4・alacritty_terminal 7.4・gpui 1.8・tako_core 0.2 | |

| 1 回 256 KiB 以上（確保の大きさ） | MB | 常駐（vmmap） |
|---|---|---|
| PTY の読み取りバッファ（30 本 × 2 MiB + 16 KiB） | 60.5 | 1 本 16 KiB = 計 0.5 MB |
| `std::fs::read`（プレビューのファイル本体の読み込み） | 12.3 | — |
| `tako_app::preview::rasterize_pdf` | 11.1 | 6.1 MB × 2 本 |
| `gpui::arena::Arena::new` | 2.0 | — |

- malloc の区分（vmmap の dirty + swap）は SMALL 92 MB・LARGE 13 MB（スタック記録の分を含む）
- **隔離した構成ではヒープは小さく、出どころの上位はプレビュー（#2009 の範囲）**。本番の 130〜408 MB との差は
  §2.1 の「解放後に持っているページ」と、実エージェントの活動で増える分（#1968 の「本番だけ 35 MB/時で増える」）

### 3.2 描画資源（論点 2）

窓の寸法だけを変えて（同じ器 1 枚・同じ中身）、出力中の footprint を測った:

| 窓（pt。tako-vd は 2 倍の HiDPI） | 1 面の大きさ（px × 4 B） | 描画の実質 | うち IOSurface（区分） |
|---|---|---|---|
| 800 × 500 | 6.4 MB | **165 MB** | 12.4 MB |
| 1600 × 1000 | 25.6 MB | **229 MB** | 74 MB |
| 2400 × 1400 | 53.8 MB | **299 MB** | 105 MB |

- **窓の画素に比例する部分は 1 面の約 2.5〜3.3 枚ぶん** = CAMetalLayer の drawable 3 枚（#819 で「正常な三重バッファ・削減は非推奨」と結論済み）
- **窓の大きさに依らない約 145〜150 MB** がある（`Owned physical footprint (unmapped) (graphics)` 148 MB・30 領域）。
  次のどれを変えても動かなかった:
  - 窓の大きさ（上の表）・**画面の大きさ**（本番の窓は内蔵 3024×1964 にあって 151 MB、隔離は tako-vd 5120×2880 で 148 MB）
  - ペイン数（器 1 枚と 4 枚で同じ 229 MB）
  - 1 フレームで描く図形の数（同じ行を `\r` で上書きするだけの出力と、画面いっぱいの出力で同じ 148 MB）
- **描いている最中しか計上されない**: 出力を止めると 40 秒前後で `phys_footprint` が 270 → 92〜117 MB へ落ち、描き始めると戻る
- **Metal の土台ではない**: デバイス + キュー + 64×64 のテクスチャへ 1 回描くだけの Swift の最小プログラムは
  描画の実質 1.5 MB（同じ区分に 56 MB の「回収可能」が出るだけ）
- GPUI のアトラスは 1024² から、instance buffer は 2 MB からなので、それ単体では 150 MB に届かない。
  正体は未確定（root が要る `footprint --unmapped` と Instruments は使えなかった）
- **本番の IOAccelerator 196 MB（再起動前）→ 40 MB（再起動後）・隔離 6 MB**: 差はプレビューの画像（PDF のラスタ・画像・動画の
  コマ）を GPU のアトラスへ載せた分と読める（再起動前はプレビューのキャッシュ 173 MB・15 件）
- **画面がロックされている間はフレームが組まれない**: 本番もロック中は本体の描画 0 回/秒（出力起因の要求は 29.6 回/秒のまま）で、
  footprint は 195 MB（描画 57 MB）まで下がっていた。
  隔離 GUI の出力中の描画の実質も 1.6 MB まで落ちた（§7 の 2・3 回目）。蓋閉じ（memory: lid-closed-no-frames）と同じく、
  描画の値はロックが解けている時にしか測れない

### 3.4 アイドル CPU と描画回数（論点 4）

- **放置**: 本体の CPU は直接 0.50〜0.55%・器 0.74〜0.90%、wakeup は 90〜96 回/秒、本体の描画は 0.02〜0.47 回/秒、電力は直接 4 mW・器 9〜11 mW。

- **何が起こしているか**: `sample` の 10 秒では全スレッドが待ちで、動いているのは `CVDisplayLink` のスレッドだけ。
  **毎 vsync** に `display_link_callback` → メインスレッドへ `gpui_macos::window::step` を投げている（描くものが無くても）。
  GPUI は窓が隠れたときだけ display link を止め、見えている間は止めない（`gpui_macos/src/window.rs`）。tako-vd は 60 Hz、
  本番の内蔵ディスプレイは 120 Hz
- **出力中**（フォーカスの無い 1 枚が 100 行/秒）: 本体の描画は 29.3〜30.4 回/秒（#1979 の上限 30 に張り付く）、本体の CPU 5.2〜7.7%、

  `sample` では `BoundsTree::insert`・`terminal_grid::plan_row`・`Scene` の並べ替え・taffy・画面のスナップショットへ薄く広がる（#1968 と同じ形）
- **出力中の器は子プロセスの CPU も使う**: 器 1 枚の出力中の 30 秒で回収済みの子が 1.05%。`sample` の `__posix_spawn` の呼び手は
  2 秒の周期処理のペインログの取り込み（`pane_log_probe_batch` = `tmux list-panes -a`・`capture_history_plain` = `tmux capture-pane`）と
