# threat model — tako remote（Tailscale Serve 方式）

> v0.6.0 で導入した Tailscale Serve ベースのリモート接続の脅威モデル。
> 旧方式（Quick Tunnel / Cloudflare relay）はすべて廃止済み。

## 信頼するもの

- **Tailscale のデーモンと tailnet のコントロールプレーン**: ノード認証・
  WireGuard 鍵交換・DERP 中継の中身を読めないことを前提とする
- **WireGuard のプロトコル**: E2E 暗号化により経路上の第三者が通信内容を復号できない
- **ループバックへのバインド**: tako daemon は `127.0.0.1:<エフェメラルポート>` だけで
  待ち受ける（#1038）。LAN・インターネットからは到達できず、外部への入口は
  `tailscale serve` が張る tailnet 内限定の HTTPS だけ。ポートは起動ごとに変わり、
  記録先（`<state_dir>/tako-remote.port`）は 0600
- **`X-Forwarded-For` / `X-Forwarded-Host` の検証（#287 P1-1）**: 層①の identity は
  serve が付与するこのヘッダに依存する
- **tako のペアリングレジストリ**: Mac ローカルの devices.json（0600）。
  ファイルの改ざんは macOS のファイル権限で防護

### ループバック TCP のトレードオフ（#1038 / #841）

v0.6.0〜v0.8.1 は UDS（socket 0600 + 親ディレクトリ 0700）のみで待ち受けており、
**別 OS ユーザーは接続自体が不能**という保証をカーネルが強制していた（#287 P1-2）。
#1038 でループバック TCP を既定にしたため、この保証は次のように変わる:

- **失われるもの**: 同一マシンの**別ユーザー / 別プロセス**も
  `127.0.0.1:<port>` へ TCP 接続できる（カーネルが遮断しない）
- **接続元プロセスの検証で埋めたもの（#841）**: serve を名乗る（= `X-Forwarded-For` が
  付いた）リクエストは、**ヘッダを identity として読む前に接続元プロセスを検証する**
  （`local_endpoint::verify_peer`。入口は `remote::forwarded_identity` の 1 実装）。
  接続の 4 つ組から所有プロセスを引き当て、①ソケットの所有ユーザーが自分自身か root
  ②実行ファイル名が tailscale デーモンのもの、の両方を満たすときだけ XFF を信じる。
  材料が 1 つでも欠けたら拒否（403）で、理由コードが監査ログ・診断ログ・
  `tako remote status` の `peer_verification` に残る。
  **unix では所有者ゲートがカーネルの事実**なので、UDS 0600 が持っていた
  「別 OS ユーザーのプロセスを排除する」性質はここで戻る。
  **Windows はソケットの所有ユーザーを引く手段が無い**ため所有者ゲートを強制できず
  （`local_endpoint::owner_check_kind()` が `unavailable` を返す）、名前のゲートだけが残る
  （下の「残存リスク（受容）」節）
- **なぜ許容したか**: macOS の GUI 版 Tailscale（`Tailscale.app` のシステム拡張）は
  **サンドボックスのためどの Unix domain socket も dial できず**、UDS では
  全リクエストが 502 になる（#1038 実測）。Windows の tailscale には
  そもそも unix socket の serve target が無い（#971）。**UDS を保ったままでは
  これらの環境で機能が成立しない**
- **残る緩和**: ①バインドは 127.0.0.1 限定（LAN へ出さない）②ポートは毎回
  エフェメラル ③管理 API（`/api/admin/*`）は `X-Forwarded-For` が付いていれば
  管理トークンが正しくても拒否する ④層②の機器ペアリング（Mac 画面での明示承認）は
  そのまま効く
- **強い分離が要る環境向けの opt-in**: standalone tailscaled しか使わないと
  分かっているなら `TAKO_REMOTE_ENDPOINT=unix` で UDS へ戻せる（挙動は v0.8.1 以前と同じ）。
  **成立するのは unix 系だけ**で、Windows は `local_endpoint::unix_supported()` = `cfg!(unix)`
  が false なので理由つきで拒否される（#971）

## 信頼しないもの

- **tailnet の他ノード（信頼できない端末が tailnet に参加した場合）**:
  二層目のペアリング認証が、Mac 所有者が明示承認していない端末を遮断する。
  未登録端末は画面データを 1 バイトも受け取れない
- **インターネット上の攻撃者**: daemon の待ち受けは 127.0.0.1 限定で、外部インタフェースには
  一切バインドしない。serve は tailnet 内限定（Funnel は使わない）。
  公開 URL はインターネットに存在しない
- **同一マシンの別ユーザー / 別プロセス**: ループバック TCP では TCP 接続自体は可能。
  ただし serve を名乗る偽の `X-Forwarded-For` は接続元プロセスの検証が弾く
  （#841。上記トレードオフ節）。管理 API は XFF 付きを常に拒否する
- **DERP 中継サーバー**: WireGuard 暗号化により中身は読めない。メタデータ
  （接続時刻・IP・転送量）は Tailscale 社が見える

## 攻撃面と対策

### Tailscale アカウント侵害

攻撃者が Tailscale アカウントの資格情報を取得した場合:

- 新しいノードを tailnet に追加できる
- しかし tako の**ペアリング層が阻止**: 未承認端末は Mac 画面のダイアログで
  許可されない限り接続できない
- **推奨**: tailnet lock を有効化（管理画面で数クリック）。新規ノードの追加に
  既存ノードの署名が必要になり、アカウント侵害だけでは参加できなくなる

### ts.net ホスト名の CT log 露出

- Tailscale が ts.net ドメインの TLS 証明書を Let's Encrypt から取得する際、
  証明書は Certificate Transparency (CT) log に記録される
- CT log には `<マシン名>.<tailnet名>.ts.net` が含まれる
- これはマシン名と tailnet 名（多くの場合ユーザーのメールアドレスに紐づく名前）を
  公開情報として露出させる
- **対策**: CT log の露出は Tailscale の仕様であり tako 側では防げない。
  ドキュメントに事実として明記し、ユーザーが判断できるようにする

### ペアリング承認の人間依存

- ペアリングの承認と role 昇格は Mac 画面（承認ダイアログ / 設定 → リモート）でのみ行える
- MCP / CLI に承認 API を**意図的に作らない**（AI がリモートアクセス権を自律的に
  付与することを構造的に防ぐ）
- この例外は `.agent/requirements.md` に明記（FR-6.5 / FR-6.21）

#### 権限の更新リクエストと昇格のゲート（#1452）

スマホの「権限が足りません」から**要求を出せる**ようにしたが（`POST /api/pair` =
#283 からある経路。新しい API は作っていない）、**要求は権限を 1 ミリも動かさない**。
上げられるのは PC の人だけ、という不変条件を 3 段で守る:

1. **方向で切る**。`POST /api/admin/devices/role` は降格・据え置きなら誰でも通し、
   **昇格は 403 `upgrade_requires_gui`**。CLI / MCP はこの経路を 1:1 で持つので、
   「上げられない」ことを**実測できる**（経路が無いと 403 という観測自体ができない）
2. **呼び出し元プロセスのゲート**。管理トークンは 0600 = **同一ユーザーなら誰でも読める**
   ので、トークンだけでは GUI と CLI / AI を区別できない。昇格しうる 2 経路
   （`/api/admin/pair/approve` と `/api/admin/devices/role`）は、接続元ソケットの
   所有プロセスを引いて（#841 の 1 実装）**実行ファイル名が `tako-app` か**を確かめる。
   判断は `remote_role::decide` の 1 関数
3. **dispatch の手前でも断る**。MCP と CLI の IPC は **tako-app の中の dispatch** で
   走るため、そこから管理 API を撃つと daemon には「tako-app からの接続」に見える
   = 2 だけでは AI を止められない。だから `remote::devices_set_role`（dispatch から
   届く唯一の口）が**自分で昇格を断る**。番犬
   `crates/tako-control/tests/issue1452_role_grant_watchdog.rs` が、昇格経路が
   CLI / MCP のソースに現れないこと・この関数が判断を先に済ませることを走査する

**このゲートが「引けない」ときは通す**（`caller_check=unavailable` として監査へ残す）。
接続元 pid を引く口が無い構成 —— `TAKO_REMOTE_ENDPOINT=unix` の UDS（tiny_http が
accept 済み fd を渡さない）—— で閉じると、**GUI からの承認そのものが不可能**になるため。
`role_change_allowed` / `role_change_denied` の各行に `caller_check` が載るので、
ゲートが効いていない通過は後から数えられる。

**受容する残り**（#1452）:

- **同一 OS ユーザーの任意プロセスは、実行ファイル名を `tako-app` にすれば GUI を騙れる**。
  名前で見るのは設置場所が環境ごとに散るため（#841 と同じ判断）。同一ユーザーの侵害は
  元から防護範囲外（その主体は `devices.json` を直接書き換えることもできる）
- **`devices.json` の直接編集**は誰にも止められない（0600 = 同一ユーザー）。
  ゲートが守るのは「tako が提供する経路」であって、ファイルそのものではない
- **UDS エンドポイントではゲートが働かない**（上記の理由で fail-open）。
  `TAKO_REMOTE_ENDPOINT=unix` を選ぶと、昇格の防護は「経路の不在 + 番犬」だけになる
- `TAKO_REMOTE_TRUSTED_ADMIN_NAMES` を置いて daemon を起動し直せば、任意の名前を
  GUI として名乗れる（隔離テスト用の口。**本番で設定しない**）

端末が書いた**理由**は承認ダイアログとユーザータスクの本文にだけ出し、
**監査ログには載せない**（FR-6.8「監査に内容を残さない」の維持）。

### daemon の listen 範囲

- daemon は 127.0.0.1 のループバック TCP で待ち受ける（#1038。外部インタフェースには
  バインドしない）。`TAKO_REMOTE_ENDPOINT=unix` で UDS（0600）へ戻せる（#287 P1-2 の形）
- **LAN 上の別端末からは接続不能**（外部インタフェースへバインドしないので経路が無い。
  既定・UDS のどちらでも同じ）
- **同一ホストの別ユーザーからの接続は、既定のループバック TCP では防げない**。
  OS のファイルパーミッションで遮断できるのは `TAKO_REMOTE_ENDPOINT=unix` を明示した
  UDS（socket 0600 + 親ディレクトリ 0700）のときだけで、既定では同一マシンの誰でも
  `127.0.0.1:<port>` へ接続できる（上の「ループバック TCP のトレードオフ」節 / #841）。
  **防げるのは「接続」ではなく「serve を名乗ること」**: 接続元プロセスの検証（#841）が
  XFF を読む前に走り、unix では所有ユーザーが自分自身でも root でもないプロセスを
  そこで落とす。検証は**エンドポイントの形で分岐**するので、`TAKO_REMOTE_ENDPOINT=unix`
  を明示した UDS 経路は（カーネルが同じ境界を強制済みなので）検証を通さない
- **tailnet / 外部から到達する経路は serve 経由だけ**（ローカルからの直結が
  既定では可能なことは上記）

### 停止経路が撃つ相手の確認（#329 / #1401）

- `tako remote stop` の kill 経路は **2 本ともが**「その PID は `tako remote serve` か」を
  確認してからでないと撃たない（正規経路 = PID ファイルの PID / stale 経路 = PID ファイルが
  消えていて `/api/health` が答えた PID）。判定は `verify_pid_identity` の 1 実装で、
  **確認できないとき**（`ps` を起こせない / 出力が空）は**撃たない**側へ倒す
- 確認できなければ state も消さず、中止の理由と手で確かめる手順を返す
  （応答しているのが本物の daemon だったときに記録を消すと到達不能にしてしまう）
- 到達条件は「PID ファイルだけが消える」+「記録済みポートの再利用」。ループバック TCP は
  同一 OS ユーザーの任意プロセスが bind できるので、隔離インスタンスと本番を並走させる
  運用では現実に起こる（同型の事故 #445）
- **残る限界**: 別 data_dir の tako daemon が同じポートを掴んでいた場合は
  `tako remote serve` として確認が通る（health は state の置き場を返さないので区別できない）。
  番犬は `crates/tako-control/tests/issue1401_stale_stop_identity_watchdog.rs`

### 入力操作の role 制限

- observe（画面閲覧のみ）は既定 role
- interact（入力・承認応答）は Mac 側で明示的に role 昇格が必要
- manage（close / resize）と admin（端末管理）はさらに上位
- role ごとに API アクセスが制限され、observe 端末が入力を試みても 403

### upload API（弾 5b）

- Interact role 必須
- サイズ上限 20MB
- 保存先はペイン cwd 配下の `.tako-remote-uploads/` 固定
- パス traversal 検証（`..` や絶対パスを拒否）
- 実行権限を付けない（0o600。所有者のみ読み書き可。#287 P2-1）
- 監査ログにファイル名を含めない（バイト数のみ。ペイン内容と同基準。#287 P2-2）
- シンボリックリンクの follow を拒否（リンク先への意図しない書き込み防止。#287 P2-4）

### タブ作成 / master 起動 API（#1078） / 「+」の 3 択（#1449）

スマホから**新しいタブとエージェントプロセスを作れる**ようになったので、
`POST /api/tabs` と `POST /api/tabs/:id/master` は close / resize と同じ **Manage role** を要求する
（observe / interact は 403。判定は `required_role` の 1 か所で、未知の POST も安全側 Manage へ落ちる）。

#1449 で「+」が 3 択（master / ターミナル / SSH ターミナル）になったが、
**通る経路は 1 本も増えていない**（ターミナル = `POST /api/tabs` だけ / SSH = #1080 の
`POST /api/ssh`）。role も **3 種とも Manage 据え置き**にした:

- 「新規起動は Interact 以上」へ緩める案は採らない。**既にペアリング済みの Interact 端末の
  権限が、UI の都合で黙って広がる**（利用者は role を見直す機会を持たない）。
  「新しいタブとプロセスを作れる」は実質シェルアクセスで、close / resize より弱くはない
- 代わりに **observe には選択肢を出さない**（押してから 403 で断られる画面を作らない）。
  出すのは理由だけで、入口そのものは隠さない（隠すと「機能が無い」と誤解させる）
- 経路の宣言は `tako_control::remote_launch::LAUNCH_ROUTES` の 1 表が正本。
  `required_role` がこの表を最初に引き、番犬
  （`crates/tako-control/tests/issue1449_launch_routes_watchdog.rs`）が
  「PWA が呼ぶ API がすべて表に在るか」をソース走査で照合する。
  **表に無い呼び口が生えたら CI が落ちる** = 未知の経路が Observe へこぼれない（#1405）

- 起動できるのは **PC 側に既に在る master プロファイル**だけ（プロファイル名以外の
  起動パラメータを HTTP から受けない）。コマンド・モデル・system prompt・env は
  すべて PC 側の設定から `orchestrator::master_launch` が組み立てる =
  **スマホから任意コマンドを実行する経路にはならない**
- 組み立てに失敗する指定（未登録プロファイル / CLI 不在 / 存在しないフォルダ）は
  **ペインに触る前**に 400 で落ちる（空のタブや `command not found` を残さない）
- 監査ログ（`<state_dir>/audit.log`）には `tab_new` / `master_launch` と
  タブ / ペイン / プロファイル名だけを書く。**cwd のパスと起動コマンド本文は書かない**
  （#287 P2-2 と同基準。起動コマンドには env の並びが載るため）
- 応答にも起動コマンド本文を入れない（同じ理由）
- app が「その要求は通らない」と答えたときは **IPC 接続を捨てない**（400 を返す）。
  捨てると利用者の入力ミスで健全な接続が落ち、次の正当な操作が 503 になる

### Claude 公式 Remote Control への委譲（#1068 / #1069 / #1077）

プロファイルで **opt-in したときだけ** claude の会話が Claude 公式の Remote Control へ繋がる
（既定 OFF）。委譲した会話は**この脅威モデルの外**へ出る:

| 観点 | tako 自前（この文書の範囲） | 委譲後（その会話だけ） |
|---|---|---|
| 経路 | tailnet 内 HTTPS（`tailscale serve` → 127.0.0.1） | Anthropic API 経由（ローカルからの outbound のみ） |
| 認証 | Tailscale identity + Mac 画面で承認した機器 | claude.ai アカウント |
| 権限粒度 | role 4 段（observe / interact / manage / admin） | **無い**（そのアカウントでログインした端末は会話を steer できる） |
| 会話の保存先 | ローカル transcript のみ | **Anthropic サーバーにも保存される** |
| 無効化 | `tako remote stop` | `disableRemoteControl` 設定 / 組織ポリシー |

- **受容リスク**: 委譲した会話には tako の role が効かない。だから既定 OFF・
  プロファイル単位の明示 opt-in にしてある（静かに外へ同期させない）
- tako が出す**ディープリンクは秘密ではない**（開くには claude.ai ログインが必要 = 実測 403）。
  ただしセッション id は `claude -p --cloud <id>` の宛先になるので、
  **診断ログ・監査ログに URL と id を書かない**（ペイン内容と同基準。番犬 =
  `crates/tako-control/tests/remote_link_watchdog.rs`）
- **委譲するのは会話だけ**。ターミナル画面（柱 2）とファイル（柱 3）は
  tako の二層認証 + role の中に残す
- PWA は opt-in を**書き換えない**（有効化はコマンドの提示だけ）。
  ユーザー設定（`remoteControlAtStartup`）も tako は書かない
### ファイル API（柱 3-E。#1079）

`GET /api/files` / `/api/files/content` / `/api/files/download` は、**ペインの画面よりも
強い持ち出し**（ファイル本体をバイト単位で tailnet 越しに配る）なので、
upload API（#285）と対の基準を置く。

- **Interact role 必須**（読み出しでも）。画面の閲覧（Observe）とファイルの持ち出しは
  危険度が別物なので、Mac 側で明示的に昇格した端末にだけ許す。observe は 403
- **読めるのは「ファイルツリーに現に出ているルートの配下」だけ**（**#1451 で
  `manage` 以上の端末だけ全体閲覧が加わった**。下の「全体のファイル閲覧（#1451）」節。
  `interact` 以下はこの節のままで、範囲は 1 ミリも広がっていない）。ルート一覧は
  daemon が溜め込まず、**毎リクエスト** tako app へ問い合わせて組む
  （`TreeFolder { action: "roots" }` → サイドバーと同じ `tree_roots_of_tab`）。
  Mac 側でペインを閉じるかピン留めを外せば**その瞬間に読めなくなる**。
  daemon 側に独自の許可リストが育たない = 画面に出ていないものは配らない
- **パスの拒否は 2 段構え**（`tako_control::remote_files`）:
  ① FS に触らない純粋関数が、絶対パス（POSIX `/` / Windows ドライブ `C:` / UNC `\\`）と
  `..` を含む形と制御文字を、ホスト OS に関係なく落とす
  ② `canonicalize` した実体が、canonicalize したルートの**配下**か（コンポーネント単位の
  比較。文字列の前方一致では `/a/bc` が `/a/b` の配下に見える）を照合する。
  **ルート内に置かれた symlink が外を指していても②で落ちる**
  （リンク自身もリンク先も 403。一覧では `escapes_root` の印を付ける）
- **符号化は認可の前に解く**（`%2e%2e` を復号せずに検査すると traversal が素通りする）
- **認可の失敗は一律 403**（404 と撃ち分けるとツリー外のファイルの**存在**が漏れる）
- **監査ログにパスを書かない**（ペイン内容と同基準。#287 P2-2）。残すのは
  種別（roots / list / content / download）と**バイト数・件数**だけで、
  ファイル名・ルート名・相対パスは 1 つも載せない。番犬
  `crates/tako-control/tests/remote_files_audit_watchdog.rs` が
  「監査への追記は `audit_payload` 経由だけ」をソース走査で機械検証する
- **応答は `Cache-Control: no-store, private`**（共有プロキシ・PWA のキャッシュへ残さない）
- **`Content-Disposition` のファイル名はヘッダに載せる前に必ず正規化**する。
  ASCII 側は英数と `.-_` だけに落とし、本来の名前は RFC 5987 の `filename*`
  （UTF-8 パーセント符号化）で渡す = 改行・引用符でヘッダを割れない
- **この節は読み出しの基準**。書き戻し（`PUT`）は下の「ファイル編集 API（柱 3-F）」、
  SSH 先のファイルは「SSH 先のファイル（柱 3-G）」で、**どちらもこの認可をそのまま通す**
- 上限: プレビュー本文 512KB（超えたら本文を返さずダウンロードへ倒す）/
  ダウンロード 512MB / 一覧 1000 件

**受容するリスク**: Interact 端末は、ツリーに出ているルート配下のファイルを
**すべて**読み出せる（`.env` や鍵ファイルがそこに在れば読める）。
（#1451 の `manage` 端末についてはさらに広い受容がある = 下の節）。ツリーに何を出すかは
Mac の所有者が決めており、role 昇格も Mac 画面での明示承認が要るので、
「昇格した端末 = そのプロジェクトを読める端末」を意図された粒度とする。
より細かい除外（`.gitignore` 準拠など）は入れていない
（除外規則が増えるほど「見えているのに読めない / 読めるつもりが読めない」がずれるため）。

### 全体のファイル閲覧（#1451）

#1079 は「読めるのは**ツリーに現に出ているルートの配下だけ**」だった。#1451 で
`#/files` から `/`（Windows はドライブごと）を辿れるようにしたが、
**#1079 の基準を捨てたのではない**: 「リモートへ配ってよいのは tako が意図的に
見せているものだけ」の**主語をツリーから role へ移した**のがこの変更の中身。

- **全体閲覧は `manage` 以上だけ**（判定の正は
  `tako_control::remote_files::FULL_BROWSE_ROLE` = `DeviceRole::Manage`）。
  `interact` 以下は**従来どおりツリーのルート配下だけ**が見える（#1079 の見え方が
  そのまま残る = 既にペアリング済みの端末の権限が黙って広がらない）。
  `observe` は引き続き全 403
- **なぜ `manage` か**: role 昇格は Mac 画面の GUI ダイアログでしか行えない
  （MCP / CLI に承認 API を意図的に作っていない = FR-6.5）ので、
  **「全体を読める端末 = Mac 所有者がその場で manage を押した端末」**が構造で保たれる。
  強さの釣り合いも取れている: `manage` は既に close / resize とタブ / プロセスの新規作成
  （#1078 / #1449）ができ、これは実質シェルアクセス = そこから `cat` できる
- **採らなかった案**: ①全 role で全体閲覧（既存 `interact` 端末の権限が UI の都合で
  黙って広がる。#1449 で同型の案を却下したのと同じ理由）②設定で ON/OFF
  （「見せる範囲」の正が role と設定の 2 本に割れる。ON にした瞬間に全 `interact` 端末へ
  一斉に広がるのは①と同じ欠点で、効くのは「manage なのに全体閲覧させたくない」端末
  だけ = その端末は `interact` へ落とせば済む）
- **通る経路は 1 本も増えていない**: 全体閲覧は `GET /api/files?root=fs&path=…` で、
  ルート id が `fs`（Windows は `fs-c`）の疑似ルートを**一覧に 1 件足すだけ**。
  パスの拒否 2 段（`check_relative_shape` → `canonicalize` + 配下判定）も
  プレビュー・編集・ダウンロード・pending / push も **#1079 の 1 実装をそのまま通る**。
  `fs` ルートでは配下判定の基準が `/` なので常に真になる = それが「全体が読める」の表現
- **認可の門は 1 か所**（`remote_files::local_roots_for`）。`fs` ルートを一覧へ足すかを
  role と A/B だけで決め、載っていなければ `resolve_in_root` が `unknown_root` で 403 にする
  = **id を推測して直接叩いても通らない**（id は秘密ではなく、認可は一覧との照合で行う）
- **ルート id の空間は構造的に分かれている**: ローカルのツリー = 12 桁 16 進 /
  SSH = `s-` / 全体閲覧 = `fs`。`s` も `fs` の 2 文字目も 16 進に無いので取り違えない
- **ショートカット（お気に入り）は読み書きとも `manage`**。ショートカットは
  **行き先の宣言であって読める範囲を広げない**が、絶対パスは画面に映らない
  在庫情報なので、全体閲覧できない端末へ配らない（#1080 で `~/.ssh/config` の
  Host 一覧を GET でも Manage にしたのと同じ判断）。永続は
  `<data_dir>/remote/shortcuts.json`（0600・`remote/` は 0700・移行の番地は
  `SchemaId::RemoteShortcuts`）で、既定（`~` / Desktop / Downloads）は
  **ファイルに書かず毎回計算する**
- **絶対パスを応答へ載せるのは全体閲覧のときだけ**（`abs`）。ツリー由来のルートでは
  従来どおり「ルート名 + 相対パス」しか返さない = 全体閲覧を許していない端末へ
  ディスク上の位置を漏らさない
- **監査ログは #1079 と同じ**（パス・ファイル名・ルート名を 1 つも載せない）。
  ショートカットの操作も種別（`shortcuts` / `shortcut_add` / `shortcut_remove`）と
  件数だけを残す
- **読めないものは黙らせない**（#1399 系）: ディレクトリごと読めなければ理由つきで断り、
  一覧の中の 1 件が読めない（`metadata` が引けない）ときは `unreadable` の印を付ける。
  0 バイトの行として静かに混ぜない
- **A/B**: `TAKO_1451_LEGACY=1`（PWA は `?tako_1451_legacy=1`）で #1079 の見え方へ戻る

**受容するリスク**: `manage` 端末は、**その OS ユーザーが読めるファイルをすべて**
tailnet 越しに読み出せる（`~/.ssh/id_*` や `.env` を含む）。#1079 の「ツリーに出している
ものだけ」より明確に広い。これを受容するのは、①`manage` への昇格が Mac 画面での
明示承認を要し、②その端末は既にタブとプロセスを作れる（= シェル越しに同じものを
読める）ため、**全体閲覧が新しく与える権限は「楽に読める」だけ**だから。
より細かい除外（`.gitignore` 準拠・機密ファイルのブラックリスト）は入れていない
（除外規則が増えるほど「見えているのに読めない / 読めるつもりが読めない」がずれる = #1079 と同じ判断）。
広すぎると感じる端末は `interact` へ落とせば #1079 の範囲へ戻る。

### ファイル編集 API（柱 3-F。#1084）

`PUT /api/files/content` は**書き込み**なので、読み出し（#1079）とは別に基準を置く。

- **Interact role 必須**（`/api/upload` と同じ。observe は 403）。認可のパス判定は #1079 の
  1 実装をそのまま通すので、書ける範囲は**読める範囲と同一**（ツリーに現に出ているルートの配下だけ）
- **daemon はファイルへ直接書かない**。PC 側の編集経路（`PreviewEdit` → `PreviewApply` →
  `PreviewSave`）を通すので、アトミックな置き換え・外部変更の検知・リモートの mode 復元・
  退避（#966）が**1 実装のまま**効く。daemon 側に 2 つ目の書き込み経路が生えない
- **競合は 2 段で見る**（窓が違う。片方だけでは素通りする組み合わせが残る）:
  ① スマホが読んだ → 保存を送った、の窓は**検証子**（`content_etag`）
  ② 適用した → 書いた、の窓は PC 側（`TextBuffer::save` / `remote_fs::save_file`）
  **検証子が無い / 合わない保存は書かずに 409**（当てずっぽうで上書きさせない）
- **検証子はスマホに計算させない**（daemon が読み出しの応答に載せて返させる）。
  暗号学的ハッシュではないが、**偽造で得られる権限が無い**ため要件にならない:
  検証子を偽れる端末は Interact 以上なので、そもそも本文に何を書いても通る。
  必要なのは「偶然の一致が起きないこと」だけなので長さ + 64bit の内容ハッシュを併記する
- **Mac 側の書きかけを踏み潰さない**: そのペインに未保存の編集があれば 409 `busy_editing`
- **テキストとして編集できるものだけ**（判定は app の `preview.mode`。daemon 側に拡張子の表を
  持たないので対応形式が増えても食い違わない）。バイナリ・画像・PDF・動画は 400 `not_text`
- **新しいファイルは作れない**（対象は実在するファイルだけ）。ディレクトリの作成・削除・
  リネームはこの API に無い（既存の `FileOp` は Mac 側 / AI の経路のまま）
- **監査ログにパスを書かない**（#1079 と同じ）。残すのは種別（write / write_denied）と
  バイト数だけで、番犬が「種別は固定文字列だけ」までソース走査で機械検証する

### SSH 先のファイル（柱 3-G。#1085）

**新しい信頼境界は増えない**: スマホは Mac の API を見るだけで、SFTP を張るのは Mac
（`remote_fs` の ControlMaster 経路）。**スマホは SSH 鍵にも known_hosts にも触らない**。

- **書き込み先・読み出し先は「`remote-folder open` 済みのフォルダの配下」だけ**。
  一覧は `RemoteFolder { action: "list" }` を**毎リクエスト**引くので、Mac 側でフォルダを
  閉じればその瞬間に読めなくなる（daemon 側に許可リストが育たない）
- **`force` をスマホから出さない**（#966 の競合検知を承知で踏み潰す操作を作らない）。
  押し出せなかった保存は**退避**され、`pending` で見えて `push` で送り直せる。
  「書けていない」を 200 で返さない（502 + `kind: "remote_pending"`）
- **ルート id は接頭辞で分ける**（`s-`）。ローカルの id は 16 進数なので `s` で始まらず、
  **id を見ただけでどちら側の認可を使うかが決まる**（取り違えの余地を作らない）
- **受容するリスク: 相手側の symlink はルートの外を指していても追える**。リモートには
  安く実体を問う手段が無いので、配下判定は文字列（絶対パス・`..`・制御文字を落として
  要素ごとに継ぐ）で行う。これは **Mac のツリー自身が同じホストに対して持っている権限と同じ**で、
  ツリーに何を開くかは Mac の所有者が決めている。書き込み側は #966 が
  「開いた記録（baseline）が無ければ書かない」でさらに閉じているので、
  **一度も認可経路を通っていないパスへは書けない**
- **受容するリスク: SSH 先のファイルは Mac のキャッシュ（`<data_dir>/remote-cache/`）へ落ちる**。
  これは #919 / #966 で既にそうなっており、スマホ経路が新しく作る露出ではない

## 残存リスク（受容）

- Tailscale 社がコントロールプレーンを通じて tailnet の構成情報を見られる
  （通信内容は WireGuard で保護されており見えない）
- DERP 中継を経由する場合、Tailscale 社がトラフィックの量・タイミングを観測できる
  （P2P 接続時はこのリスクは軽減される）
- CT log に ts.net ホスト名が記録される（上記。macOS のホスト名を一般名にすることで
  軽減可能だが、完全な防止は不可能）
- ローカルの root / 管理者権限を持つ攻撃者は daemon のプロセスメモリや
  devices.json を直接読み書きできる（OS レベルの侵害であり tako の防護範囲外）
- 同一 OS ユーザーの悪意あるプロセスと root は、ローカルエンドポイントへの接続・
  token / devices.json の直接読み取りが可能（OS レベルの侵害であり tako の防護範囲外。
  従来どおり）
- **別 OS ユーザーからの daemon への到達（TCP 接続そのもの）は、既定
  （ループバック TCP）では受容するリスク**。同一マシンなら誰でも
  `127.0.0.1:<port>` へ接続できる。ただし **serve を名乗って層①を騙ることは
  接続元プロセスの検証（#841）が止める**: unix では所有ユーザーが自分自身でも root でも
  ないプロセスからの XFF 付きリクエストは 403 になる（緩和の全体像は
  「ループバック TCP のトレードオフ」節）。
  接続そのものをカーネルで塞げるのは `TAKO_REMOTE_ENDPOINT=unix` を**明示**して
  UDS（socket 0600 + 親ディレクトリ 0700）にしたときだけ（#287 P1-2 の形。socket の
  権限は `platform::local_endpoint` の `bind_unix` / 親ディレクトリは `remote::state_dir`）。
  **Windows にはその opt-in が無い**（`local_endpoint::unix_supported()` = `cfg!(unix)`）。
- **Windows では接続元の所有ユーザーを引けないので、所有者ゲートが効かない（#841 の残り）**。
  `GetExtendedTcpTable` で接続元 pid と実行ファイル名までは引けるが、その pid の
  トークン SID を読むには別の権限が要るため、**名前のゲートだけ**が残る。
  実行ファイルを `tailscaled.exe` と名付けた別ユーザーのプロセスは通ってしまう。
  `tako remote status` の `peer_verification.owner_check` が `unavailable` と名乗るので、
  効いていないことは実行時に読める。塞ぐには pid → トークン SID の引き当てが要り、
  Windows 実機での検証が前提になる（Windows 全体は #467 配下）。
  **v0.8.1 以前は UDS が既定だったのでこの項は「到達する経路が無い」と書いてあった**が、
  #1038 で既定が変わった時点でその前提は失効している（判定の正は
  `tako_control::remote::parse_endpoint_spec(None)` = 番犬
  `crates/tako-control/tests/issue1406_threat_model_endpoint_watchdog.rs`）
