# threat model — tako remote（Tailscale Serve 方式）

> v0.6.0 で導入した Tailscale Serve ベースのリモート接続の脅威モデル。
> 旧方式（Quick Tunnel / Cloudflare relay）はすべて廃止済み。

## 信頼するもの

- **Tailscale のデーモンと tailnet のコントロールプレーン**: ノード認証・
  WireGuard 鍵交換・DERP 中継の中身を読めないことを前提とする
- **WireGuard のプロトコル**: E2E 暗号化により経路上の第三者が通信内容を復号できない
- **ループバックへのバインド**: tako daemon は `127.0.0.1:<エフェメラルポート>` だけで
  待ち受ける（#1038）。LAN・インターネットからは到達できず、外部への入口は
  `tailscale serve` が張る tailnet 内限定の HTTPS だけ。ポートは起動ごとに変わり、
  記録先（`<state_dir>/tako-remote.port`）は 0600
- **`X-Forwarded-For` / `X-Forwarded-Host` の検証（#287 P1-1）**: 層①の identity は
  serve が付与するこのヘッダに依存する
- **tako のペアリングレジストリ**: Mac ローカルの devices.json（0600）。
  ファイルの改ざんは macOS のファイル権限で防護

### ループバック TCP のトレードオフ（#1038 / #841）

v0.6.0〜v0.8.1 は UDS（socket 0600 + 親ディレクトリ 0700）のみで待ち受けており、
**別 OS ユーザーは接続自体が不能**という保証をカーネルが強制していた（#287 P1-2）。
#1038 でループバック TCP を既定にしたため、この保証は次のように変わる:

- **失われるもの**: 同一マシンの**別ユーザー / 別プロセス**も
  `127.0.0.1:<port>` へ接続できる。偽の `X-Forwarded-For` を付ければ層①を
  通過しうる（詳細と対処方針は #841）
- **なぜ許容したか**: macOS の GUI 版 Tailscale（`Tailscale.app` のシステム拡張）は
  **サンドボックスのためどの Unix domain socket も dial できず**、UDS では
  全リクエストが 502 になる（#1038 実測）。Windows の tailscale には
  そもそも unix socket の serve target が無い（#971）。**UDS を保ったままでは
  これらの環境で機能が成立しない**
- **残る緩和**: ①バインドは 127.0.0.1 限定（LAN へ出さない）②ポートは毎回
  エフェメラル ③管理 API（`/api/admin/*`）は `X-Forwarded-For` が付いていれば
  管理トークンが正しくても拒否する ④層②の機器ペアリング（Mac 画面での明示承認）は
  そのまま効く
- **強い分離が要る環境向けの opt-in**: standalone tailscaled しか使わないと
  分かっているなら `TAKO_REMOTE_ENDPOINT=unix` で UDS へ戻せる（挙動は v0.8.1 以前と同じ）

## 信頼しないもの

- **tailnet の他ノード（信頼できない端末が tailnet に参加した場合）**:
  二層目のペアリング認証が、Mac 所有者が明示承認していない端末を遮断する。
  未登録端末は画面データを 1 バイトも受け取れない
- **インターネット上の攻撃者**: daemon の待ち受けは 127.0.0.1 限定で、外部インタフェースには
  一切バインドしない。serve は tailnet 内限定（Funnel は使わない）。
  公開 URL はインターネットに存在しない
- **同一マシンの別ユーザー / 別プロセス**: ループバック TCP では接続自体は可能なので、
  層①を騙られうる（#841。上記トレードオフ節）。管理 API は XFF 付きを常に拒否する
- **DERP 中継サーバー**: WireGuard 暗号化により中身は読めない。メタデータ
  （接続時刻・IP・転送量）は Tailscale 社が見える

## 攻撃面と対策

### Tailscale アカウント侵害

攻撃者が Tailscale アカウントの資格情報を取得した場合:

- 新しいノードを tailnet に追加できる
- しかし tako の**ペアリング層が阻止**: 未承認端末は Mac 画面のダイアログで
  許可されない限り接続できない
- **推奨**: tailnet lock を有効化（管理画面で数クリック）。新規ノードの追加に
  既存ノードの署名が必要になり、アカウント侵害だけでは参加できなくなる

### ts.net ホスト名の CT log 露出

- Tailscale が ts.net ドメインの TLS 証明書を Let's Encrypt から取得する際、
  証明書は Certificate Transparency (CT) log に記録される
- CT log には `<マシン名>.<tailnet名>.ts.net` が含まれる
- これはマシン名と tailnet 名（多くの場合ユーザーのメールアドレスに紐づく名前）を
  公開情報として露出させる
- **対策**: CT log の露出は Tailscale の仕様であり tako 側では防げない。
  ドキュメントに事実として明記し、ユーザーが判断できるようにする

### ペアリング承認の人間依存

- ペアリングの承認と role 昇格は Mac 画面の GUI ダイアログでのみ行える
- MCP / CLI に承認 API を**意図的に作らない**（AI がリモートアクセス権を自律的に
  付与することを構造的に防ぐ）
- この例外は `.agent/requirements.md` に明記

### daemon の listen 範囲

- daemon は 127.0.0.1 のループバック TCP で待ち受ける（#1038。外部インタフェースには
  バインドしない）。`TAKO_REMOTE_ENDPOINT=unix` で UDS（0600）へ戻せる（#287 P1-2 の形）
- LAN 上の別端末・同一ホストの別ユーザーからは接続不能（OS のファイルパーミッションで強制）
- serve 経由（tailnet 内）のアクセスのみが到達する

### 入力操作の role 制限

- observe（画面閲覧のみ）は既定 role
- interact（入力・承認応答）は Mac 側で明示的に role 昇格が必要
- manage（close / resize）と admin（端末管理）はさらに上位
- role ごとに API アクセスが制限され、observe 端末が入力を試みても 403

### upload API（弾 5b）

- Interact role 必須
- サイズ上限 20MB
- 保存先はペイン cwd 配下の `.tako-remote-uploads/` 固定
- パス traversal 検証（`..` や絶対パスを拒否）
- 実行権限を付けない（0o600。所有者のみ読み書き可。#287 P2-1）
- 監査ログにファイル名を含めない（バイト数のみ。ペイン内容と同基準。#287 P2-2）
- シンボリックリンクの follow を拒否（リンク先への意図しない書き込み防止。#287 P2-4）

### ファイル API（柱 3-E。#1079）

`GET /api/files` / `/api/files/content` / `/api/files/download` は、**ペインの画面よりも
強い持ち出し**（ファイル本体をバイト単位で tailnet 越しに配る）なので、
upload API（#285）と対の基準を置く。

- **Interact role 必須**（読み出しでも）。画面の閲覧（Observe）とファイルの持ち出しは
  危険度が別物なので、Mac 側で明示的に昇格した端末にだけ許す。observe は 403
- **読めるのは「ファイルツリーに現に出ているルートの配下」だけ**。ルート一覧は
  daemon が溜め込まず、**毎リクエスト** tako app へ問い合わせて組む
  （`TreeFolder { action: "roots" }` → サイドバーと同じ `tree_roots_of_tab`）。
  Mac 側でペインを閉じるかピン留めを外せば**その瞬間に読めなくなる**。
  daemon 側に独自の許可リストが育たない = 画面に出ていないものは配らない
- **パスの拒否は 2 段構え**（`tako_control::remote_files`）:
  ① FS に触らない純粋関数が、絶対パス（POSIX `/` / Windows ドライブ `C:` / UNC `\\`）と
  `..` を含む形と制御文字を、ホスト OS に関係なく落とす
  ② `canonicalize` した実体が、canonicalize したルートの**配下**か（コンポーネント単位の
  比較。文字列の前方一致では `/a/bc` が `/a/b` の配下に見える）を照合する。
  **ルート内に置かれた symlink が外を指していても②で落ちる**
  （リンク自身もリンク先も 403。一覧では `escapes_root` の印を付ける）
- **符号化は認可の前に解く**（`%2e%2e` を復号せずに検査すると traversal が素通りする）
- **認可の失敗は一律 403**（404 と撃ち分けるとツリー外のファイルの**存在**が漏れる）
- **監査ログにパスを書かない**（ペイン内容と同基準。#287 P2-2）。残すのは
  種別（roots / list / content / download）と**バイト数・件数**だけで、
  ファイル名・ルート名・相対パスは 1 つも載せない。番犬
  `crates/tako-control/tests/remote_files_audit_watchdog.rs` が
  「監査への追記は `audit_payload` 経由だけ」をソース走査で機械検証する
- **応答は `Cache-Control: no-store, private`**（共有プロキシ・PWA のキャッシュへ残さない）
- **`Content-Disposition` のファイル名はヘッダに載せる前に必ず正規化**する。
  ASCII 側は英数と `.-_` だけに落とし、本来の名前は RFC 5987 の `filename*`
  （UTF-8 パーセント符号化）で渡す = 改行・引用符でヘッダを割れない
- **この節は読み出しの基準**。書き戻し（`PUT`）は下の「ファイル編集 API（柱 3-F）」、
  SSH 先のファイルは「SSH 先のファイル（柱 3-G）」で、**どちらもこの認可をそのまま通す**
- 上限: プレビュー本文 512KB（超えたら本文を返さずダウンロードへ倒す）/
  ダウンロード 512MB / 一覧 1000 件

**受容するリスク**: Interact 端末は、ツリーに出ているルート配下のファイルを
**すべて**読み出せる（`.env` や鍵ファイルがそこに在れば読める）。ツリーに何を出すかは
Mac の所有者が決めており、role 昇格も Mac 画面での明示承認が要るので、
「昇格した端末 = そのプロジェクトを読める端末」を意図された粒度とする。
より細かい除外（`.gitignore` 準拠など）は入れていない
（除外規則が増えるほど「見えているのに読めない / 読めるつもりが読めない」がずれるため）。

### ファイル編集 API（柱 3-F。#1084）

`PUT /api/files/content` は**書き込み**なので、読み出し（#1079）とは別に基準を置く。

- **Interact role 必須**（`/api/upload` と同じ。observe は 403）。認可のパス判定は #1079 の
  1 実装をそのまま通すので、書ける範囲は**読める範囲と同一**（ツリーに現に出ているルートの配下だけ）
- **daemon はファイルへ直接書かない**。PC 側の編集経路（`PreviewEdit` → `PreviewApply` →
  `PreviewSave`）を通すので、アトミックな置き換え・外部変更の検知・リモートの mode 復元・
  退避（#966）が**1 実装のまま**効く。daemon 側に 2 つ目の書き込み経路が生えない
- **競合は 2 段で見る**（窓が違う。片方だけでは素通りする組み合わせが残る）:
  ① スマホが読んだ → 保存を送った、の窓は**検証子**（`content_etag`）
  ② 適用した → 書いた、の窓は PC 側（`TextBuffer::save` / `remote_fs::save_file`）
  **検証子が無い / 合わない保存は書かずに 409**（当てずっぽうで上書きさせない）
- **検証子はスマホに計算させない**（daemon が読み出しの応答に載せて返させる）。
  暗号学的ハッシュではないが、**偽造で得られる権限が無い**ため要件にならない:
  検証子を偽れる端末は Interact 以上なので、そもそも本文に何を書いても通る。
  必要なのは「偶然の一致が起きないこと」だけなので長さ + 64bit の内容ハッシュを併記する
- **Mac 側の書きかけを踏み潰さない**: そのペインに未保存の編集があれば 409 `busy_editing`
- **テキストとして編集できるものだけ**（判定は app の `preview.mode`。daemon 側に拡張子の表を
  持たないので対応形式が増えても食い違わない）。バイナリ・画像・PDF・動画は 400 `not_text`
- **新しいファイルは作れない**（対象は実在するファイルだけ）。ディレクトリの作成・削除・
  リネームはこの API に無い（既存の `FileOp` は Mac 側 / AI の経路のまま）
- **監査ログにパスを書かない**（#1079 と同じ）。残すのは種別（write / write_denied）と
  バイト数だけで、番犬が「種別は固定文字列だけ」までソース走査で機械検証する

### SSH 先のファイル（柱 3-G。#1085）

**新しい信頼境界は増えない**: スマホは Mac の API を見るだけで、SFTP を張るのは Mac
（`remote_fs` の ControlMaster 経路）。**スマホは SSH 鍵にも known_hosts にも触らない**。

- **書き込み先・読み出し先は「`remote-folder open` 済みのフォルダの配下」だけ**。
  一覧は `RemoteFolder { action: "list" }` を**毎リクエスト**引くので、Mac 側でフォルダを
  閉じればその瞬間に読めなくなる（daemon 側に許可リストが育たない）
- **`force` をスマホから出さない**（#966 の競合検知を承知で踏み潰す操作を作らない）。
  押し出せなかった保存は**退避**され、`pending` で見えて `push` で送り直せる。
  「書けていない」を 200 で返さない（502 + `kind: "remote_pending"`）
- **ルート id は接頭辞で分ける**（`s-`）。ローカルの id は 16 進数なので `s` で始まらず、
  **id を見ただけでどちら側の認可を使うかが決まる**（取り違えの余地を作らない）
- **受容するリスク: 相手側の symlink はルートの外を指していても追える**。リモートには
  安く実体を問う手段が無いので、配下判定は文字列（絶対パス・`..`・制御文字を落として
  要素ごとに継ぐ）で行う。これは **Mac のツリー自身が同じホストに対して持っている権限と同じ**で、
  ツリーに何を開くかは Mac の所有者が決めている。書き込み側は #966 が
  「開いた記録（baseline）が無ければ書かない」でさらに閉じているので、
  **一度も認可経路を通っていないパスへは書けない**
- **受容するリスク: SSH 先のファイルは Mac のキャッシュ（`<data_dir>/remote-cache/`）へ落ちる**。
  これは #919 / #966 で既にそうなっており、スマホ経路が新しく作る露出ではない

## 残存リスク（受容）

- Tailscale 社がコントロールプレーンを通じて tailnet の構成情報を見られる
  （通信内容は WireGuard で保護されており見えない）
- DERP 中継を経由する場合、Tailscale 社がトラフィックの量・タイミングを観測できる
  （P2P 接続時はこのリスクは軽減される）
- CT log に ts.net ホスト名が記録される（上記。macOS のホスト名を一般名にすることで
  軽減可能だが、完全な防止は不可能）
- ローカルの root / 管理者権限を持つ攻撃者は daemon のプロセスメモリや
  devices.json を直接読み書きできる（OS レベルの侵害であり tako の防護範囲外）
- 同一 OS ユーザーの悪意あるプロセスと root は、socket への接続・token /
  devices.json の直接読み取りが可能（OS レベルの侵害であり tako の防護範囲外。
  従来どおり）。別 OS ユーザーによる daemon への到達経路は UDS 化（#287 P1-2）で
  消滅した
